# Universal Code Analysis Agent

通用代码分析智能体。目标是一个能自主分析代码项目、调用工具、执行编译/测试并根据结果继续推理的 Agent。

**9.5 阶段把评估集从 9 条扩到 43 条，并按模型窗口给 chunk 切段——先修「量不出来」，再修「截断」。** 9.4 结束时四组检索器在 7 条正例上全是 6/7：尺子被打满了，embedding 有没有用、分段有没有用，一个数字都看不出来。新 case 集 **37 条正例 + 6 条反例**：正例里 25 条语义（不说符号名、不说文件名）、12 条词法，语言上 Python 30 / C++ 7（`tests/fixtures/cpp` 下 13 块的迷你环形缓冲区工程，作为独立语料 `cpp_fixture`，生产索引按忽略名单不扫 `fixtures/`），每条带 `language` / `query_lang` / `query_type` / `corpus` 可选元数据（老文件照常读），报告多出「分组结果」几行（整体 / 语言 / 查询语言 / 查询类型 / 语料 / 反例）——**Hit@1/3/5 的定义一个字没改**。分段（新模块 `index/segments.py`）：紧凑文本按行装进「窗口 − 2 token」的预算，位置行 `path:symbol [kind]` 每段都带，单行超预算按字符硬切；token 数是**估计**（汉字 1 字 1 个、其余 2 字符 1 个；2793 块上实测 100% 不低于真实分词）——因为查缓存必须能在不加载模型的前提下算出 key。打分从「整块一个向量」改成「段间取最大」，缓存 key 加 `#s0/#s1…`、命名空间加分段策略版本（`--no-segment` 一键复现 9.4）。**真实分词器数超窗：多语言模型 1481/2973（49.8%）→ 0/6633（0.0%）；英文模型 49/2973（1.6%）→ 0/3380。** 但命中率**没有变好**：43 条上 Hit@1/3/5 分别是字面 10/12/12、假 embedding 10/12/12、本地英文模型 11/13/13、多语言 **9.4 的 11/12/12 → 9.5 的 10/12/12**——分段让 `fsync` 从第 1 掉到第 2（每个块都有更多段可以「碰巧像」，max 会抬所有块的上限），让 `从缓冲区里取出一条最旧的数据` 从「一条都没有」变成「类块排第 1」（仍不算命中）。分段的收益落在两处：超窗归零，以及 8.5 那条白鲸的目标块相似度——`SymbolIndex.read_verified` 对「校验文件有没有被改过」整块 0.2339 → 段间最大 **0.3034**（+29.7%），但**仍低于 0.35 的阈值，这条还是没查到**：瓶颈已经从「喂进去的文本被截掉」变成「这个模型对这条中文查询的判别力」。耗时：首轮（空缓存）多语言预热 48.1 s → 75.6 s（嵌入 3016 → 6676 条），重复（全命中）`embed()` 调用 0 次、整轮 1m14.4s → 1m28.0s、单条检索均摊 222.4 → 396.0 ms。反例量出两件诚实的事：**英语整句在这份语料上做不了反例**（测试方法名就是英文整句，`how`/`to`/`in`/`from` 全在里面，字面打分必然命中——`SELECT * FROM users WHERE id = 1`、`kubectl delete pod` 两条实测假阳性后换成了中文整句和标识符样的词）；真模型则在 **3/6 条反例上假阳性**（`missing_symbol_zzz`、`kubernetes_ingress_controller`、`ffmpeg 转码`），英文模型还把 `量子纠缠` 捞出 1 条——语义检索确实改写了「查不到」的定义。`retrieval.py`（含权重、阈值）、`Retriever` 排序、`CodeChunk` / `SymbolIndex`、`Agent` / `RepairLoop` / `Verifier`、`SearchChunksTool` 的输出格式**一个字节没改**，没换模型、没引向量库、没动 chunk 边界。新增 85 条离线测试（`tests/test_segmentation.py` 44 + `tests/test_evaluation_groups.py` 41），全套 1669 条全绿。

**9.4 阶段把 9.0~9.3 建的 embedding 线正式接进了 Agent 的 RAG。** `SearchChunksTool` 多了一个可选参数 `embedding`，四种模式 `off / fake / local / multilingual`，从环境变量 `SEARCH_CHUNKS_EMBEDDING` 读（写 `.env` 或直接设），**默认 `off`——不选就是 8.8 起的老行为，一个字节不差**（测试拿 `DEFAULT_SCORERS` 在同一个项目上逐条比对）。开着的时候语义分只是 scorer 列表里多出来的第四条（8.6 定的形状），**`search_code_chunks` 的返回格式还是那五段；`retrieval.py`（连权重都没动）、`Retriever` / `CodeChunk` / `SymbolIndex` / `Embedder` 接口、RepairLoop / Verifier 一个字节没改**。**模型懒加载**：构造 / 注册 / Agent 启动都不碰模型，第一次真检索才加载；**坏了自动退**——模型没装、下不动、缓存文件损坏、打分中途抛异常，一律由新增的 `DegradingScorer` 兜住、退回字面检索，错因记在 `tool.embedding_error` 里，工具照常出结果。紧凑文本 / 批量预热 / VectorCache 全部复用 9.3 的现成件（新增 `cache_for()` 统一命名空间规则，评估入口同一条路）。真实计时（2780 块语料）：冷缓存首次查询 **57.9 s**（其中模型加载 38.8 s，剩下是建索引 + 全量预热），同进程重复查询 **270 ms**；换个新进程、缓存全命中时**模型根本不加载**，首次查询 **643 ms**、重复 **195 ms**（`embed()` 调用 0 次）。真实 Agent 验证：英文 + 中文两条查询都自发走 `search_code_chunks → read_file`，分别答出 `index/retrieval.py:247-266` 和 `index/retrieval.py:258`，行号逐条回查正确。新增 35 条离线测试（`tests/test_search_chunks_embedding.py`），全套 1584 条全绿。

**9.3 阶段把 embedding 的三个开销问题一起治了：喂什么文本、怎么批量、怎么不重算。** 给 embedding **单独拼一段紧凑文本**（`index/compact.py`：位置行 `path:symbol [kind]` + docstring 压平截断 + 代码开头，**`chunk.code` 一个字节没改**）——2709 块的语料上 tokenizer 实测：英文模型超窗 462/2709（17.1%）→ **41/2709（1.5%）**，两个模型的平均长度 207 / 205 token 都降到 **128**（多语言模型超窗 46.3% → 49.1%：它的窗口只有 128 token，超窗条数降不下来是模型选型的事，9.2 已记；拼法能保证的是「截掉之后剩下的全是有效信号」）。**docstring 要从代码开头里掏空**是实测逼出来的：同一段文字喂两遍，超窗比例反而 46.2% → 51.2%，多语言组 Hit@1 掉到 5/7，掏空后回到 6/7。批量：打分前一次 `prefetch()`，**2718 条文本只产生 10 次 `embed()` 调用**（1 次全量预热 + 9 条查询），不再是 N 个 chunk N 次单条调用，**Embedder 接口没动**。缓存：`index/vector_cache.py` 把向量按命名空间（`LocalEmbedder:模型名#compact-v1`，假货用词表指纹）写进 `~/.cache/universal-code-agent` 的 JSON，chunk key 带 `digest`、查询 key 独立——**改文件 / 换模型 / 改拼法都自动失效**，缓存读写失败只降级（baseline 和关键字检索照常），缓存目录在项目外不会被索引扫到，不提交任何向量数据。四组评估 Hit@1/3/5 **还是 6/7 全平**：首轮（空缓存）整进程 100 s、单条查询均摊 **205.8 / 215.0 ms**（L6 / L12，9.2 是 6593.8 / 11702.1 ms），重复一轮（全命中）整进程 **4 s**、`embed()` 调用 **0 次**、模型连加载都没有，**冷热两轮结果逐字相同**。`retrieval.py`、CodeChunk / SymbolIndex、Agent / RepairLoop / Verifier / Tool 一个字节没改，没换模型、没接向量库、没动 chunk 边界、没调权重；新增 45 条离线测试（`tests/test_embedding_optimization.py`），全套 1549 条全绿。

**9.2 阶段把多语言模型接进评估，四组同台验证「中文的语义分到底能不能用」。** 新增 provider `"multilingual"`（默认 `paraphrase-multilingual-MiniLM-L12-v2`，模型名可配）——评估入口只给 provider 名字，模型选择全在 `index/providers.py` 一张表里，9.0 留的口第一次真正用上（复用 `LocalEmbedder`，一行注册 + 一行默认值，**没写新类**）。`python -m index --multilingual` 让四组——字面 / 假 embedding / 英文模型 / 多语言模型——跑在同一个 ChunkIndex、同一组 case、同一个 Evaluator 上：Hit@1/3/5 **四组全是 6/7、6/7、6/7**，平均耗时 20.0 / 33.3 / 6593.8 / 11702.1 ms。**多语言模型的中文能力是真的**：同一条中文查询，英文模型的全库相似度挤在 0.35–0.41 的噪声带里，多语言模型拉到 0.5887（最高）~0.2954（均值）~-0.0196，前 8 名从「随机」变成清一色验证 / 检查语义相关的块。但 8.5 的靶子「校验文件有没有被改过」**依然没进前 5**，探针把原因也钉死了：目标块 `read_verified` 整块 368 token，而多语言模型 `max_seq_length` 只有 128（全库 45.7% 的块超限被截），整块嵌入又被路径 / 符号名 / 英文签名稀释（同一查询：整块 0.2273 vs 只留中文 docstring 0.3265），排到 2092/2616；同一句译成英文反而排 259/2616。**结论：模型的语言短板补上了，新瓶颈在「喂什么文本、截多长」——切块文本设计和更大上下文的模型是下面的事。** Embedder 接口、`retrieval.py`、`embedding.py` 评分逻辑、chunk、Agent、Tool 一个字节没改；新增 17 条离线测试（`tests/test_multilingual_embedding.py`）；全套 1504 条全绿。模型文件不提交（在 HuggingFace 缓存目录里），不做 cache、不引向量库。

**9.1 阶段拿真模型量了 RAG 的实际效果，结论是「管线通了，模型语言不对」。** 新增三组对比入口：`python -m index`（字面 baseline）/ `--hybrid`（再加假 embedding）/ `--local`（再加真 `LocalEmbedder`），同一个 case 集、同一把尺子。三组的 Hit@1 / Hit@3 / Hit@5 **全是 6/7、6/7、6/7，一条没差**；平均耗时 19.9 ms → 32.6 ms → **9129.1 ms**（真模型第一条现场把全项目的块 embed 一遍填缓存——不做 embedding cache 是这一阶段明令的限制）。8.5 留到现在的靶子「校验文件有没有被改过」**真模型照样没打中**，临时探针（跑完即删）把原因照了出来：`all-MiniLM-L6-v2` 是英文单语模型，对中文查询 + 满篇中文注释的项目几乎没有区分度——这条查询下全库语义相似度挤在 0.35–0.41 的噪声带里（第一名竟是 `_newline`）；把它译成英文再查，语义分立刻有用武之地，把名字相关的块顶到第 1（109.08，其中 15.08 来自语义）。**机制是活的，缺的是模型的语言能力**——这正是 9.0 的 provider 抽象留着要解决的问题：换多语言模型只改一个模型名。Retriever 排序、Embedder 接口、Agent / Tool / RepairLoop 一个字节没改；新增 7 条离线测试（`tests/test_evaluation_entry.py`），真模型不进测试；装上 sentence-transformers 之后全套 1487 条测试仍然全绿。

**9.0 阶段把 embedding provider 做成可插拔的，并接上第一个真模型实现（本地）。** 8.6 留的 `Embedder` 接口（`dimension` + `embed`）一个字没改，`FakeEmbedder` 原样保留；新增 `LocalEmbedder`（`index/local_embedding.py`）：包一个本地 sentence-transformers 模型，**模型细节不出这个文件**（对模型只要求 `encode` + `get_sentence_embedding_dimension` 两个方法），**加载是懒的**（构造不碰模型不联网，第一次 embed 才加载；没装库就报 `EmbeddingUnavailable`，写清怎么装）——sentence-transformers 是可选依赖、没进 requirements.txt，**没装也能跑全部测试**。`index/providers.py` 是工厂：`create_embedder("fake")` / `create_embedder("local")` 按名字拿 Embedder，将来接 API provider 就是「写一个 Embedder 子类 + 往注册表加一行」。新增 22 条离线测试（`tests/test_embedding_providers.py`）：工厂行为、批量输入输出对应、维度、模型只加载一次、空输入不惊动模型、缺库 / 加载失败的报错、失败不粘住，以及挂着假模型的 LocalEmbedder 直接塞进 `hybrid_scorers` 在真 `Retriever` 上跑通——**retrieval 的排序逻辑、Agent / RepairLoop / Verifier / 工具链路一个字节没改**，不引入向量数据库、不做 cache（下一阶段）。

**8.9 阶段不加功能，拿真模型验一件事：8.8 接进来的 RAG，Agent 到底用不用。** 真项目上跑了 3 个只读分析任务（问「tool-calling 循环在哪儿」「+10 的粒度奖励在哪儿定义」「怎么判断索引文件被改过」），**3/3 都是自发先调 `search_code_chunks`、再 `read_file` 精读，答案里的文件 / 函数名 / 行号逐条回查正确**；临时小工程和一份项目副本上跑了 3 个修改任务，工具序列是 `search_code → read_file → edit_file → 自动 run_tests`——目标都是 `__pycache__`、`htmlcov` 这类**叫得出字面**的东西，按 8.8 定的分工（关键词找单行用 `search_code`）这选择是对的，**所以提示词没有改**（「发现不主动使用 RAG 才允许最小改 prompt」，没触发）。检索线、工具设计、Agent 逻辑一个字节没改；新增 4 条离线测试（`tests/test_rag_flow.py`）：提示词把 RAG 排在「缩范围」这一步，以及 `RAG 定位 → read_file → edit_file → 自动验证` 的完整链。探针脚本（真调 LLM 的那个）是临时的，用完即删没进仓库。

**8.8 阶段把 Code RAG 接进了 Agent。** 8.1~8.7 建的检索线一直在 `index/` 里自己玩，Agent 够不着——这一步加了一个普通工具 `SearchChunksTool`（`search_code_chunks`）：查询交给 `index.Retriever`，结果转成一行行位置信息回灌给模型。**只给位置不给正文**（`相对路径:起止行号` 符号 [类型] 分数 命中原因）——省上下文，也让模型拿行号去 `read_file` 现读磁盘上的当前代码，而不是索引里那份快照。注册进 `ToolRegistry` 后走的就是既有的那条 `ToolExecutor` 的路；**检索逻辑（`index/`）一个字节没改，已有工具的代码一行没改，Agent / RepairLoop / Verifier 也没碰**——动过的只有装配处：`tools/__init__.py`、`main.py` 和系统提示词里「先用哪些工具缩小范围」那一句（提示词和注册表有对账测试，新增工具不点名字就红）。全部测试离线可跑。

**8.7 阶段修了排序里最别扭的一个毛病：大块压小块。** 8.5 量出来的两条「答案被它自己的类挡住」，根子是**类块的正文含着它所有成员的正文**——方法里的那句话，必然也出现在包着它的类块里，两边命中同样的分，再按行号排，类就压在了方法上面（要的是方法，拿到的是包着它的一大坨）。修法只动 `index/retrieval.py` 的打分和排序，切块一行没碰：**有正文命中的 function / method 多给一档 +10 的粒度奖励**（`Match("specific", ...)`），类 / 结构体不给；奖励刻意小于「名字里的词」（28 < 30），正文命中再怎么攒也翻不过名字命中。另外把**整名命中**（查询和符号名一模一样）单独排成第一档——它和别的命中不是同一种证据，不该被凑出来的总分盖过（测试拿硬塞的 999 分钉着）。效果：**Hit@1 4/7 → 6/7**，8.5 诊断的那两条（「把文件读回来」「fsync」）都从第 2 升到第 1；Hit@3 / Hit@5 不变（6/7），耗时不变（~19 ms）。唯一还查不到的还是那条真·人话「校验文件有没有被改过」——ranking 解决不了「答案根本不在候选里」，那条留给真 embedding。

**8.6 阶段给检索加了语义打分——先用一个假 embedding 把 hybrid 管线跑通。** 8.4 说「加 embedding 就是再写一个 scorer 塞进去」，这一步真写了：`index/embedding.py` 定义 `Embedder` 接口（文本 → 向量，批量进批量出）和 `EmbeddingScorer`，把 embedding 包成 retrieval 认的 `(Query, CodeChunk) -> [Match]`——余弦相似度 × 权重、过阈值才给分。**但没有接任何模型**：实现是一个 `FakeEmbedder`，一张手写的「同义词小抄」，每组词算一个概念，撞上哪几组那几个维度就是 1。`Retriever(scorers=hybrid_scorers(...))` 就是在原来三个字面打分器后面接上它；不接，行为和 8.4 一字不差（`retrieval.py` 这一阶段一个字没改——8.4 留的口就是这个口）。效果用 8.5 那把尺子量：**Hit@1 4/7 → 5/7**，「把文件读回来」从第 2 名升到第 1（类块的概念更多、被余弦稀释，让位给了方法自己），代价是平均耗时 18.8 → 30.9 ms。但两条诚实的结论也钉进了测试：8.5 留的那个靶子「校验文件有没有被改过」假货**照样打不中**（790 条命中里目标排第 102），反例 `missing_symbol_zzz` 反而被语义捞出 5 条（查询里含着真词 `symbol`）——假货证明的是**接口通**，不是**语义有用**；后一个问题留给真模型。

**8.5 阶段给检索配了把尺子。** 8.4 的检索好不好，之前只能靠翻几条结果「感觉还行」——感觉没法比较，以后调权重、换 embedding，凭什么说新的比旧的好。`Evaluator` 拿一组手写 case（一句查询 + 期望命中的目标）挨条跑 `Retriever`，看目标落在第几名，汇总成 **Hit@1 / Hit@3 / Hit@5** 和平均耗时。自带 9 条 case，覆盖文件名 / 符号 / 类 / 函数 / 功能描述（两条，一条用词对得上、一条是人话）/ 代码关键词 / 反例。当前基线：**Hit@1 4/7、Hit@3 6/7、Hit@5 6/7**，两条反例都确实没查到，平均 ~18 ms——那 3 条没进第 1 名的是这份评估最有价值的部分（两条是「答案被它自己的类挡住」，一条真·描述查询压根查不到，正好是 embedding 的靶子）。case **存 JSON 不写在 py 里**：这个项目把自己也索引了，查询字符串写成 Python 常量就会跟着模块的 chunk 一起进索引，等于把答案埋进考卷。评估**只调用** `Retriever.search()`，打分和排序一个字没动；不是工具、不进 Agent，不含 embedding / 向量库。`python -m index` 就能跑一遍。

**8.4 阶段把检索接上了。** 前三层都在建索引（有哪些文件 → 有哪些符号 → 代码正文），`Retriever` 是**第一个查的入口**：给一句查询，返回排好序的 `SearchResult`（命中的 chunk、总分、以及**为什么命中**）。四种匹配全是字面的——symbol 简单名、qualified symbol、文件路径、chunk 正文；查询先拆好（剥掉首尾标点、小写、拆词），分数是一张拍出来的权重表，「名字就叫 `run` 的」永远压过「正文里恰好出现过 `run` 的」。排序同分时按 路径 → 行号 钉死，跑一百遍顺序一样。打分函数是**一串可替换的 `(Query, CodeChunk) -> [Match]`**：以后加 embedding 就是再写一个这样的函数塞进去，排序和 `top_k` 一行都不用改。它**只在现成的 chunk 上找**，不重扫源码、不重切块，同样不是工具、不进 Agent，不含 embedding / 向量库 / 语义搜索。

**8.3 阶段把符号切成了代码块。** 前两层只记「哪儿有什么」，`ChunkIndex` 这一步才把**代码正文**取出来：一个类 / 函数 / 方法一段，边界就是符号的行范围，正文按这个范围从文件里真读出来（不拿符号名拼、也不拿摘要糊）。读文件和 8.2 用同一个 `read_verified`——digest 对不上就整段不切，宁可没有 chunk，也不给一段行号错位的代码。嵌套符号（类里套方法）保留成父子两块，只有行范围**完全一样**时才去重；没有符号的文件本阶段不切，扩展点留在一处注释上。同样**不是工具、不进 Agent**，不含 embedding / 向量库 / 语义搜索。

**8.2 阶段在文件清单之上建了符号索引。** `SymbolIndex` 把已索引文件里的类、函数、方法记成结构化记录（`Symbol`：名字、类型、路径、起止行、所属文件的摘要、父级），Python 走 `ast`、C/C++ 走原来那套逐行扫描，两边各一份实现、和 `code_summary` 共用。它只认 `ProjectIndex` 里 `status=indexed` 的文件，读回来先核对 `digest`——文件被改过就整个跳过，宁可一个符号不给，也不给拿旧行号切出来的过期数据。行号是要拿去切代码的，所以有测试把全项目的每一条符号切出来、验「名字确实在这段范围里」。同样**不是工具、不进 Agent**，不含 embedding / 向量库 / 语义搜索 / 切块。

**8.1 阶段开始给代码检索打底。** 新增 `index/` 包，只做一件事：`ProjectIndex` 把项目扫一遍，每个文件记成一条结构化记录——相对路径、语言、状态、大小、修改时间、内容摘要（sha256 前 16 位）。它复用 `list_files` / `search_code` 那套遍历规则和路径边界（同一个 `check_root`、同一个 `iter_files`），二进制 / 超大 / 读不动的文件也留一条、写明为什么没收，只有收进来的才出现在 `files()` 里。它**不是工具、不进 Agent**，也不存文件内容、不含 embedding / 向量库 / 语义搜索——那些在后面几步（Symbol Index → Code Chunk → 检索）。

**7.8 阶段把「一轮」的定义补齐了。** 7.5 起的规矩是「先有个坏掉的东西才算修复轮」，于是模型没先编译、直接改完第一次验就过的那种，记录里写成 0 轮——明明一次就改好了，翻记录却像什么都没干。现在**一次 `edit_file` 加上它触发的那次验证就是一轮**：改完第一次验就过的记成「一轮通过」（`RepairRound.one_shot`，摘要里念「第 1 轮就通过」），先坏后修的还是老样子。`Repair Summary`、最终回答和 Repair History 的 JSON 用的是同一个数，不会再对不上。

**7.7 阶段把修复过程留了档。** 以前这些只活在内存和屏幕上：`run()` 一返回，几轮、改了哪儿、卡在哪一关、为什么停，就只剩那几行文字了。现在每跑完一次 `run()` 就写一份 JSON 到项目根目录下的 `repair_history/`（目录不存在会自己建，文件名是时间 + 一小段随机数，**一份一个文件、绝不覆盖**）。写进去的东西全部照抄 `RepairRound`：轮次、文件、改动位置、指纹、验证命令、退出码、诊断变化、编译 / 构建和测试两关的结果，外加这次的状态、停止原因和那句 Repair Summary。写历史是**附带**的事——目录建不出来、盘满、文件被占着，都只在 `history.last_error` 里留一句话，用户的任务照常返回，修复结果一个字不变。

**7.6 阶段让「修好了」变得可信。** 编译通过不再等于修好：C/C++ 的改动是**两关**——先编译 / 构建，这一关过了再跑一次 `run_tests`，两关都过才叫修好（`Verification.ok`）。测试失败和编译失败一样进修复循环：测试输出喂回给模型、记进这一轮的记录、接着修或者按规矩停。同时给每轮改动记一个**指纹**（哪个文件、动了哪几行、换成了什么），同一次改动又做一遍就停下——模型在两个写法之间来回横跳时（A 改成 B、又改回 A），指纹会重回来。修完（或停下）时给最终回答加一句 Repair Summary：几轮、每轮卡在哪一关、最后成没成。

**7.5 阶段把「验不过就接着修」接上了。** 验证没过不再只是摆给模型看：还欠着一次没修好的时候，模型想收尾会被按回去接着改（一条新消息，把「已消失 / 仍在 / 新增」重新说一遍），改完自动再验一次，直到修好、或者修不动为止。停的规矩有五条：用满 `max_repair_rounds`（默认 5，和 `max_steps` 是两个概念）、同一次改动又做了一遍（7.6 起）、连着两轮看到的一模一样、文件改完一个字节没变、模型两次只回话不动手。停下来的地方代码保留最后一次修改的样子，**不自动回滚**，并把每一轮都摊开说清楚（第几轮、改了哪儿、用哪条命令验的、退出码多少、诊断比上一轮变了什么）。

**7.4 阶段把「改完要验」这一步接上了。** `edit_file` 改完一处代码，Agent 会自己接着跑一次验证：C/C++ 用它上次编过的那条命令重编（没有就先看工程里有没有构建系统，有就 `build`、没有才 `compile`），Python 跑 `run_tests`。结果附在同一条消息后面：过没过、原来那条错消失没有、有没有新冒出来的。判断是**在文本上比**的，不是看行号——行号常常整段挪位，按行号比会把「同一条错挪了一行」说成「旧的没了、又来一条新的」。这一轮只跑一次：不循环、不自动回滚、不自动再改（那是下一步的事）。

**7.3 阶段给了 Agent 一个改代码的工具。** `edit_file` 是第一个会**改**项目文件的工具：按一段唯一匹配的原文替换，或者按行号替换（行号和 `read_file` 是同一套）。它只改指定的那一处——匹配 0 次或多次都直接报错，不猜；编码、换行、文件其余部分一个字节都不动；写入走临时文件 + 原子替换，不会有半个文件留在盘上。

**7.2 阶段让 `build` 也接上了诊断。** `build` 的结果末尾同样会另附一段一行一条的诊断，用的还是 `tools/diagnostics.py` 那一个解析器——没有为构建输出再写一套。构建比单文件编译更值得解一遍：一个失败能牵出一串连带错误，而 `msbuild` 报的是绝对路径（`read_file` 只认相对 root 的路径），还会在结尾把每条诊断再汇总说一遍。所以在 `build` 这边多做了两件小事：路径换成本地的，说重了的并掉。

**6.9 阶段让 `code_summary` 支持了 C/C++。** 除了 Python，现在也能给 `.c` / `.h` / `.cpp` / `.hpp` 出结构摘要：`#include`、`namespace`、`class` / `struct` / `union` / `enum`、函数声明与定义，每条都带行号（和 `read_file` 同一套，可以直接拿去引用位置）。没有用 Clang，是在 `tools/cpp.py` 里逐行扫出来的**近似**结果——宏展开、宏生成的名字、复杂模板认不出来，宁可漏也不能报错。Python 那部分一行没动。

**6.8 阶段给 `read_file` 的返回值加了行号。** 每行形如 `42|代码内容`，宽度按文件总行数对齐。行号是给模型拿去引用位置的——之前 `read_file` 返回不带行号的原文，模型只能自己数行，而它数不准。提示词里那条引用规则也改成了「以 `read_file` 返回的为准」。

**工具侧在 6.7 阶段补齐了工程构建。** 到 7.3 为止一共九个工具：列目录、读文件、搜内容、看结构、跑命令、跑测试、编译、构建，再加一个改文件。前四个是只读的，共用同一套路径访问边界和遍历/解码规则，都支持 `path` 参数限定范围；`run_command` 是第一个会真的动系统的工具，能跑构建、跑测试、调编译器，跑太久会被强制终止，输出过长会掐掉中间保留首尾；`run_tests`、`compile`、`build` 是它的三个特化版——命令由工具自己拼，模型给的是「跑测试」「编译哪个文件、用什么编译器、加什么参数」「用哪个构建系统」，不是命令本身。工具执行统一走执行层，每次调用都会被记录；发给模型的历史经过裁剪，不会因为对话变长而超限。

**7.0 阶段把 Windows 上的 MSVC 接上了。** `compile` 多了第三个编译器 `cl.exe`，`build` 多了个构建系统 `msbuild`。两个都藏在 Visual Studio 里、都不在 PATH 上，用之前得先跑一遍 `vcvars64.bat` 把 `PATH` / `INCLUDE` / `LIB` 铺好——这部分在 `tools/vsenv.py`。装没装 VS 由微软自己的 `vswhere.exe` 回答，所以代码里不出现任何具体的 VS 版本号或安装路径。

**7.1 阶段把编译输出读成了结构。** 编译器说「哪个文件、第几行、什么问题」，但三个编译器把这件事写成两种格式。`tools/diagnostics.py` 把它们都认下来，`compile` 的结果末尾会另附一段一行一条的诊断，行号可以直接拿去 `read_file` 核对。原始输出一个字符不动。

## 一次 run() 发生了什么

```
用户输入
  → messages → ContextManager.build() → LLM（带上工具 schema）
  → 模型要求调用工具？
      是 → Agent → ToolExecutor → ToolRegistry → Tool
           → 改的是代码文件？→ Verifier 接着跑一次验证，附在结果后面
                               （C/C++：先编译 / 构建，过了再跑 run_tests）
           → 验没过？→ RepairLoop 记一轮：改完自动再验，模型想收尾会被按回去接着修
                        （两关都过 / 到上限 / 改动重复 / 连着两轮一样 / 文件没变 → 停）
           → ToolResult 转成 tool 消息回灌 → 回到「发给 LLM」这一步
      否 → 返回最终回答
  → 装了 RepairHistory 的话，把这一轮的修复过程写一份 JSON 到 repair_history/
    （写不进去只留一句警告，不改这一轮的结果）
```

`self.messages` 始终是完整历史，只有发出去的那一份是裁剪过的。

一轮里最多循环 `max_steps`（默认 15）次，超出就抛 `AgentError` 并回滚这一轮的全部消息。工具报错（名字不存在、参数不对、除零）不会让 Agent 崩溃，错误文本会作为工具结果回灌给模型，让它自己决定重试还是换个说法。工具实现自己有 bug 抛出的意外异常同样被兜住，只是错误文本里会带上异常类型，方便你排查。

## 说明

- 不使用 LangChain、LangGraph 等 Agent 框架，Agent Runtime 自行实现。
- Agent 只保留当前进程内的会话历史，退出即丢失，也没有持久化。
- 工具已经接进 LLM 调用：注册进 `ToolRegistry` 的工具会自动转成 schema 发给模型，由模型决定何时调用。命令行里问 `(3+4)*3` 会真的走 `CalculatorTool`，模型自己不做算术。
- 文件类工具有统一的访问边界（`tools/paths.py`）：构造时定一个 `root`（默认项目根目录），所有路径参数必须落在 root 以内。判断放在 `resolve()` **之后**，所以 `..`、绝对路径、符号链接三种逃逸方式一起被堵住。错误文本会回灌给模型。
- `ListFilesTool` 默认跳过 `.git`、`.venv`、`__pycache__`、`node_modules`、`build` 等噪音目录（本项目 `.venv` 有 2500+ 个文件，全列出来只会淹没上下文），并统一返回相对 root 的 `/` 分隔路径，方便直接交给 `read_file`。
- `ReadFileTool` 按 `utf-8-sig` → `gbk` 顺序尝试解码（覆盖 BOM 和中文 Windows 的 GBK 源码），含 NUL 字节或两种编码都解不开的文件按二进制拒绝。读取上限 256 KB、返回上限 40000 字符，一旦截断会在末尾说明截断原因——否则模型会以为拿到的是全文。
- `ReadFileTool` 返回的每一行前面都带行号，形如 `42|代码内容`，宽度按**整个文件**的行数对齐（1000 行的文件是 `   1|`）。加行号是因为模型自己数行数不准——实测过：让它说某段代码在第几行，给的行号大半是错的，而引用错一行就等于把人指到隔壁。宽度按全文算而不是按这次返回了几行算，否则同一个文件截断前后同一行的编号会变，模型对不上。
- 切行先把 `\r\n` 归一成 `\n`，行尾就不会挂着一个看不见的 `\r`；数行用 `split("\n")` 而不是 `splitlines()`——后者把 `\x0c` 这类字符也当换行，而换页符在老的 C 代码里是当分页用的，断在那儿行号就和编辑器对不上。末尾那个空串不算一行（文件以换行结尾时 `split` 会多给它一个）。这套规则放在 `tools/textfile.py` 的 `split_lines()` 里，`search_code` 数的行号必须和它一致，有测试钉着这条。
- 截断按**整行**丢，不按字符砍：砍到半行的话末尾那行是残的，「只返回了第 1–N 行」这句话也就不成立了。末尾会写清实际返回的行号范围（`…（文件共 3000 行，只返回了第 1–812 行）`）；字节上限和字符上限同时触发时，行数只说「读到的部分」——那时根本不知道全文有多少行。只返回一行时不写「第 1–1 行」，写「第 1 行」。
- 如果第一行本身就超过返回上限（整份压成一行的文件，比如压缩过的 JS），工具**不返回正文**，只给一句说明。硬塞四万个字符的乱码只会白占上下文，说清楚「这文件是一整行」更有用。
- 行号前缀也占那 40000 字符的额度，所以能读到的正文比加行号之前少一点（大约一成）。不这么算的话工具的输出会超出自己的上限，`ContextManager` 就会把末尾那句截断说明再砍一次，模型反而不知道这只是半份文件。
- `SearchCodeTool` 的输出格式是 `相对路径:行号: 内容`（如 `tools/calculator.py:42: return result`），第一段可以直接拿去喂 `read_file`，方便「搜到 → 读全文」两步连起来。
- `SearchChunksTool`（8.8）是检索那条线接进 Agent 的入口：查询交给 `index.Retriever`，每条结果一行「`相对路径:起止行号` 符号 [类型] 分数 命中原因」，**不给代码正文**——拿到行号自己去 `read_file` 读原文，省上下文，读到的也永远是磁盘上当前的代码。和 `search_code` 的分工：后者按关键词找单行，它按符号名 / 路径 / 正文综合排序找整块（整个方法 / 类），适合问「X 在哪儿实现」。
- 四个文件类工具都支持 `path` 参数，语义一致：相对项目根目录、必须在 root 以内、默认整个项目。搜索限定子目录时（`search_code(keyword="socket", path="src/network")`），报出来的路径**仍然相对 root**——相对子目录的话，拿去喂 `read_file` 就找不到文件了。
- 搜索默认不区分大小写，需要精确匹配时传 `case_sensitive=true`；默认最多返回 100 条匹配、每个文件最多读 1 MB，超出会在末尾说明。
- 搜到解不开的文件（二进制、非 UTF-8/GBK）就跳过它继续搜下一个，绝不让一个坏文件中断整次搜索。
- 单个文件读不动（权限、被占用）就跳过它，但**整次遍历**失败（目录进不去）会转成 `ToolError`——不是裸抛 `OSError`。裸抛会绕开「错误文本回灌给模型」这条路，直接让 Agent 崩掉，和 list_files / code_summary 的行为也不一致。
- 行号用 `text.split("\n")` 数，不用 `splitlines()`——后者会把 `\x0c` 等字符也当换行，数出来的行号会和编译器不一致。这条规则和 `read_file` 共用同一套说法（`tools/textfile.py` 的 `split_lines()`），两个工具报出来的行号必须是同一个数，否则模型按 `search_code` 的结论去 `read_file` 里核对时会对不上。
- `CodeSummaryTool` 分两套：`.py` 走标准库 `ast`，`.c` / `.h` / `.cpp` / `.hpp` 走 `tools/cpp.py` 的逐行扫描。两边都只取定义、不取函数体：先看清骨架再决定读哪个文件，比逐个 `read_file` 省得多。输出用缩进表示嵌套层级：

  ```
  agent/agent.py:
    class Agent
      def run
      def _run_loop
  ```

  ```
  include/renderer.h:
     6|#include "vector3.h"
    10|namespace render
      12|class Renderer
        18|draw(const math::Vec3& position, const math::Vec3& direction, double fov) const
  ```

- `ast` 把 `except` / `case` 的子句建模成独立节点（`ExceptHandler` / `match_case`），不是 `Try` / `Match` 的直接子节点。只看直接子节点会漏掉 `try: ... except ImportError: def fallback()` 这种常见写法，所以 `_definitions()` 会对所有语句节点继续下潜、但不增加层级。
- C/C++ 那套每条都带行号，数法和宽度都跟 `read_file` 一样（都走 `tools/textfile.py` 的 `split_lines()`），模型可以直接拿去引用位置。行号报的是**名字所在的那一行**，不是「这段声明从哪一行开始」——`template <...>` 和返回类型常常另起一行，报起始行的话模型去那一行核对时什么都对不上。有测试拿 `read_file`、`search_code` 对着钉这一条。
- 扫描前先把每行变成**两份**文本，长度一一对应，用同一套下标同时操作：**代码版**把注释和字符串都换成空格，数括号只看它（注释里的花括号、字符串里的括号都不能参与层级计算）；**干净版**只换注释、留着字符串，因为识别出来的东西要给模型看，参数里的 `"hi"` 不该显示成一串空格。原始字符串 `R"(...)"` 里有花括号和引号，整体跳过。
- `#define` 里的花括号不是代码里的花括号。预处理指令整行不参与扫描，反斜杠续行的下一行也跟着排除——不这么做的话，一条宏就能让后面所有东西的层级错位，而且宏结束时还会多弹一次栈。
- 源码按括号深度为 0 的 `;` `{` `}` 切成一段段「声明」，参数表跨行的签名就是这样拼回来的（`draw(int x,` / `int y) const {` 拼成一条）。行号换算靠段里留着的换行——名字前面有几个换行，就是起始行往后第几行。
- 开出 `{` 的段压栈、`}` 弹出，**函数体里**一律不算结构，不然函数体里每个函数调用看着都像函数声明。分界线是「栈里有没有 `function`」，不是「当前深度是不是 0」——命名空间里也有一堆深度为 1 的声明。命名空间下的 λ 没有外层函数挡着，靠段里的 `=` 认出它是代码不是声明。
- 认不出来的宁可不报：`template <class T>` 里的 `T` 后面是 `>` 不是 `{`，`struct Point p;` 里的 `Point` 后面是变量名——这类都靠「名字后面必须跟 `{` `:` `;` 或 `final`」这一条挡掉。`friend class B;` 单独排除，它声明的不是自己的成员。`public:` / `private:` 后面不跟分号，会和下一条声明粘成一段，但粘着不影响报出来的行号，所以没为它单开分支。
- 函数签名只留 `名字(参数) 限定词`，返回类型不要：`static inline std::vector<std::string> ` 这一串太占地方，要看它 `read_file` 就行；参数必须留下，两个重载之间就靠它区分。括号里以数字或引号开头的是「用括号初始化成员」（`int port_(8080);`）而不是函数声明，也靠这条挡掉。
- 正则碰上一段又长又配不上括号的文本，回溯会退化成平方级，几万字符就足够让工具卡住。所以单段超过 2000 字符直接不认——宁可漏一条。有测试钉着「很长的一段是跳过，不是卡住」。
- ⚠️ C/C++ 这部分明确不支持的：宏展开（`PROPERTY(int, value);` 会当成函数）、宏生成的名字、复杂模板、函数指针、`operator[]` 这类怪名字、一段里写多个声明符（`Widget(), ~Widget();` 只认第一条）、函数体里定义的局部类型。漏一条不影响别的条目，也不会让工具崩。
- 语法错误、非文本、过大的文件都只标注在它自己那一段（`（语法错误，已跳过）`），其余文件照常分析。省略会让模型以为文件不存在。
- 工具执行统一走 `ToolExecutor`（`Agent → ToolExecutor → ToolRegistry → Tool`）。Agent 的推理循环因此不用再关心「工具会不会炸」——执行、兜异常、记耗时都在执行层做完，循环里只剩「把 `ToolResult` 转成回灌消息」一件事。
- `ToolError` 和意外异常分开处理：前者是工具按预期拒绝（参数不对、路径越界），错误文本原样回灌；后者是工具实现有 bug，错误文本会带上异常类型（如 `ZeroDivisionError: division by zero`），既让模型知道这次失败了，也让你一眼看出是自己的代码问题。`KeyboardInterrupt` 之类不捕获——那是用户要中断，不该被吞掉。
- `ToolResult` 是 frozen dataclass，创建后不可改，避免执行完的结果在半路被就地篡改。耗时用 `time.perf_counter()` 测量，它是单调时钟，不受系统时间调整影响。
- 执行层还查一件事：工具**必须返回 `str`**。`execute()` 忘了写 `return` 会返回 `None`，不拦的话 `None` 会一路进到请求体里才炸，那时候已经离现场很远了。检查用 `isinstance(content, str)`（不是 `type() is str`），str 的子类是合法返回值。
- 命令行里的 `print_trace` 放在 `try/finally` 里，不是放在 `try` 后面。工具连续报错、轮数超限这些最需要看记录的场景全是走异常分支出去的，写在 `try` 后面根本轮不到执行。正常返回时顺序不变，仍然是先打记录再打回答。
- `Trace` 刻意做得很小：只有一种事件（`tool_call`）和一个容器，不做通用事件系统。一次 `run()` 一个 `Trace`，用 `agent.get_trace()` 拿。
- 记录动作放在 `ToolExecutor._record()` 一处，成功和失败走同一条路——分散在多个 `return` 前面写，早晚会漏掉一条分支。
- 每轮 `run()` 换一个**新的** `Trace` 对象，而不是清空旧对象。这样上一轮如果你还拿着那个列表，它不会被这一轮悄悄改掉。测试里专门钉了这条。
- `run()` 失败（LLM 报错、轮数超限）时消息历史会回滚，但 Trace 不回滚——回滚是让对话能重试，Trace 记的是真实发生过的事，删掉就没法排查了。
- `tools/executor.py` 顶层不 `from agent.trace import Trace`，只在 `TYPE_CHECKING` 里导入。因为 `agent` 和 `tools` 本来就互相引用，运行时再互相导入就成环了：谁先被 `import` 会决定成败，非常脆。执行层只调 `trace.record_tool_call(...)`，不需要认识 `Trace` 这个类。
- 上下文裁剪在 `ContextManager` 里（`agent/context.py`），只做两件事：单条 tool 结果太长就截断（默认 5 万字符），总量还超就从最老的整轮工具调用开始删（默认 10 万字符）。不引入 RAG、向量库、长期记忆、LLM 摘要——这一版只保证请求不会因为历史太长而超限。
- `ContextManager.build()` 不改原始 `messages`，返回的是新列表和新字典。所以裁剪到哪一步都不影响 `agent.messages`、不影响回滚、不影响下一轮：每次都拿完整历史重新算。测试里用 `deepcopy` 快照钉了这条。
- 裁剪必须**整组**删：assistant 要求调用工具的那条，和它后面几条 tool 回复算一组，同进同出。只删 tool 回复会留下「要求了调用却没有结果」的残缺结构，接口会直接拒掉整个请求。测试在 1/2/3/5 轮各种长度下断言「被要求过的 `tool_call_id` 集合 == 收到了回复的集合」。
- 永远不删：system、最后一条用户消息、最后一组（可能是正在进行中的这一轮）。剩下的都删光了还超，就宁可稍微超一点发出去，也不把对话结构删坏。
- 单条上限 5 万字符是**刻意**比 `ReadFileTool.max_return_chars`（4 万）宽松的：否则 read_file 自己写在末尾的「只读了前一部分」会被再砍掉一次，模型就不知道这个文件本来就只读了一半。
- 截断说明必须点明「不是完整结果：原有 N 字符，只发送了前 M 个」。只说「已截断」不够——模型会以为读到的是全文，然后拿残缺内容下结论。
- `RunCommandTool` 用 `subprocess.run(..., shell=True, capture_output=True)`，不用 `os.system`：后者拿不到 stdout / stderr，只能把输出直接喷到终端上，模型什么都看不见。`shell=True` 是为了能直接跑带参数、`&&`、管道的命令字符串。
- 命令的工作目录固定在工具的 `root`（默认项目根目录），和另外四个工具的边界是同一个概念：相对路径不会溜到项目外面去。`check_root()` 顺带挡掉了「把 root 设成 `C:\`」这种开局就失控的配置。
- `check=False` 是刻意写出来的：退出码非 0 不是异常，是**结果**。跑测试失败、编译报错都是 Agent 要读到并据此继续推理的信息，抛异常等于把它变成「工具坏了」。
- 命令输出的解码和 read_file 不一样：read_file 解不开就拒绝，命令输出解不开则退化成「认不出的字节换成 �」继续返回。因为命令输出本来就可能是二进制 dump、彩色控制符、进度条，直接拒绝等于把整条结果丢掉，连退出码都看不到了。
- 标准输出和标准错误**各有各的 2 万字符额度**，超出就掐掉**中间**、保留开头和结尾，并在原处标注省略了多少字符。保留结尾是必须的——跑测试时 `3 failed, 374 passed` 这种结论在最末尾，只留开头等于把最有用的一句扔了。退出码在头部，不在被掐的范围里。
- 两路加起来的 4 万字符仍然低于 `ContextManager` 的单条上限（5 万），所以工具自己写好的截断说明不会被上下文层再砍一次。这个跨层的关系有测试钉着。
- 退出码非 0 时结果里会多写一句「（非 0，命令失败）」，省得模型只盯着输出内容、把「命令其实没成功」看漏。
- `run_command` 有超时：默认 30 秒，调用时可以传 `timeout` 覆盖（跑完整构建、全量测试时用得着）。超时按**正常结果**返回，不抛异常——「这条命令超时了」是模型要读到并据此改主意的信息，和退出码非 0 一样属于结果。
- 超时用的是 `Popen` + `communicate(timeout=)`，**不是 `subprocess.run(timeout=)`**，也不是 `with` 语句。这两个选择都是实测出来的，不是风格偏好：
  - `subprocess.run(timeout=)` 在 Windows + `shell=True` 下超时是**假的**。它内部 kill 掉 shell 之后，还会再调一次 `communicate()` 收残余输出，而 shell 的子进程还占着管道没退出，那一下会一直等到命令自己跑完。实测：设 1 秒的超时，8 秒后才返回。
  - `with subprocess.Popen(...)` 退出时会 `close()` 管道，而管道还有个读取线程堵在 `read()` 上，主线程得排队等它。实测：设 0.3 秒的超时，`close()` 又堵了 4.73 秒。
  - 所以超时路径上是：`communicate(timeout=)` 准时叫停 → `kill()` 动手 → `wait()` 回收 shell → 立刻返回，**绝不碰管道**。有回归测试钉住「0.3 秒的超时必须在 3 秒内返回」。
- ⚠️ 超时杀掉的只是 **shell**，被它启动的子进程可能还活着（Windows 上尤其明显：`cmd.exe` 死了，下面的 `python` 还在跑）。彻底解决要用进程组 / Job Object，属于后面的事。当前后果是：超时后可能残留一个进程，而且它会一直占着工具 root 目录。
- ⚠️ 超时那条路径上拿不到任何输出——命令被终止时输出留在了管道里，而读它就会踩到上面那个坑。结果里会明说「输出没有保留」，不会假装命令什么都没输出。
- `CalculatorTool` 用 AST 白名单求值而非 `eval()`，因为表达式之后会由 LLM 生成，属于不可信输入。
- `TestTool`（工具名 `run_tests`）自己一行执行逻辑都没写，内部持有一个 `RunCommandTool` 并把活全交给它。subprocess、超时、输出解码、截断说明都已经在那边踩过坑也测过了，这里再抄一份等于把坑也抄一份。这一层只做一件事：把「跑测试」这个动作固定成一条确定的命令。
- 「跑哪条命令」是钉死的常量，模型改不了——`parameters` 里根本没有 `command`，模型能传的只有 `timeout`。要换命令只能在装配时改（`TestTool(command=...)`），那是人的决定，不是模型的决定。这一版只支持 `python -m unittest discover -s tests -t .`，不支持 pytest。
- 默认超时 120 秒，比 `run_command` 的 30 秒宽松：跑测试天然更慢（本项目 700+ 条用例约 20 秒），慢一点只是多等一会儿，给少了则会把一次本来正常的测试跑判成超时，白等一轮还得重来。
- 结果**原样返回** `run_command` 的文本，不另加一层包装。「命令、退出码、标准输出、标准错误」这四样它本来就都有，再套一层只会让模型看到两份格式。有测试钉着这条。
- 测试不通过（退出码非 0）不算调用失败，和 `run_command` 一致——「有测试挂了」是模型要读到并据此继续推理的信息，抛异常等于把它变成「工具坏了」。
- 这一版不解析测试结果（不把 `Ran 2 tests` / `FAILED (failures=1)` 抽成结构化字段）。那段文本模型自己看得懂，先加解析等于替它做它已经会做的事。
- `CompileTool`（工具名 `compile`）和 `TestTool` 一样，执行全交给 `RunCommandTool`，自己一行 subprocess 都没写。区别在命令：`run_tests` 那条是钉死的常量，`compile` 这条是**拼出来**的——模型给的是源文件名，命令由工具生成。
- 因为命令是拼的，`compile` 比另外两个多一道校验：路径参数除了要落在 root 以内（`paths.py` 管这个），还必须只由字母、数字、下划线、点、横线、斜杠组成。`paths.py` 管的是「能不能指到项目外面」，管不了「文件名里塞一个 `&` 会发生什么」——命令是拼成字符串交给 shell 的，一个带 `;` 的文件名就能把后面的东西变成另一条命令。用白名单不用黑名单：漏掉一个特殊字符就全废了。
- 命令里出现的一律是**校验过之后重新拼出来的相对路径**，不是模型原样递进来的那一串。`compile(source="./main.cpp")` 生成的命令里写的是 `main.cpp`。
- 代价是带空格、中文的文件名编译不了，会拿到一个说清原因的 `ToolError`。第一版接受这个限制——要放开得先做正确的 quoting，那是另一件事。
- 用哪个编译器的优先级是：**这次调用指定的 > 装配工具时指定的 > 自动找**（`g++` → `clang++` → `cl`）。和 `timeout` 是同一套规则——调用级的参数盖过工具自带的默认值，越具体越优先。自动找也失败时在**执行时**报 `ToolError`，不是装配时：放在构造时报的话，机器上没装编译器会让 `main.build_agent()` 直接起不来，整个 Agent 跟着废掉；装没装编译器是环境的事，不该让 Agent 装不起来。
- `cl` 排在最后不是随手排的。用它得先起一次 `cmd` 跑 `vcvars64.bat` 铺环境（这台机器上实测 2.5 秒），而机器上真装了 `g++` 的话，那一秒多纯属白付。装了两个就按这个顺序挑，想换可以显式传 `compiler`。
- 编译器名字是唯一一个**只能是清单里那几个**的参数，因为它是除了路径之外第二个会被拼进命令的词：`compiler="g++; whoami"` 和路径参数是同一类风险。装配时传的那个不走这道校验——那是代码写的配置（测试还要靠它塞一个假编译器进去），模型传的才算不作数的输入。两个信任级别用两条规则，不是漏洞。
- 点名要的编译器还得真的装着，否则直接报错说清楚「没有它，装了的是 X」。不查的话模型拿到的是 shell 那句「不是内部或外部命令」——看得懂，但它分不出是名字写错了还是根本没装、装了哪个。
- `flags` 的校验分两步：先过字符白名单（字母数字加上 `- = . , + / :` 和空格；引号、分号、与或、重定向、反引号、`$`、括号全不放行），再逐个 token 拒掉 `-o` / `--output` / `-MF` / `-MT` / `-MQ` 以及 cl 那边的 `/Fe:` `/Fo:` `/Fd:` `/Fa:` `/Fi:` `/Fr:` `/Fm:`。**拒掉而不是默默忽略**：模型以为自己指定了输出名、实际没被采纳，比直接报错更难排查。
- 白名单里的 `/` 和 `:` 是给 MSVC 写法留的（`/std:c++17`）。它们不是 shell 的元字符，放进来不会改变命令的意思。
- 命令拼出来的顺序是 `编译器 [flags] 源文件 -o 输出`——flags 在最前，`-o 输出` 在最后。这样即使哪天校验放松了，后面那个 `-o` 也会盖掉前面混进来的。产物写到哪儿是由命令的**结构**保证的，不只是靠上面那道校验。
- `-O2` 和 `-o` 只差一个大小写：前者是优化级别，后者才是输出。前缀匹配大小写敏感，不会误伤。
- flags 会先归一化空白（`"  -O2   -Wall  "` → `-O2 -Wall`）再拼命令，免得拼出两个连续空格或者空 token。
- 输出名省略时沿用源文件的目录和名字（`src/app.cpp` → `src/app`）。Windows 上 MinGW 会自己补 `.exe`；结果里的编译命令写着 `-o src/app`，模型照着这条命令就能推出产物在哪。
- 编译不通过（退出码非 0）不算调用失败，和 `run_command` 一致——编译器报的错（含出错的文件名和行号）正是模型要读到并据此改代码的信息。
- 这一版不做 CMake、Makefile、多文件工程、编译缓存、自动修错、C++ AST 分析，都留给后面。
- `BuildTool`（工具名 `build`）是第一个要跑**一串**命令的工具：cmake 得先配置再编译。前一步退出码非 0 就停下，并明说「剩下 N 步没有执行」——配置都没过还去编译，只会拿一堆连带错误把真正的原因淹掉。
- 为了知道「这一步过没过」，`RunCommandTool` 这一版多了个 `run_with_code()`，返回 `(退出码, 结果文本)`；`execute()` 就是丢掉退出码的那一半。前面几个工具都是「跑一条、把文本原样交出去」，从来不关心退出码，所以一直没暴露过它。
- 超时被杀掉的命令没有退出码可言，`run_with_code()` 返回 `None`。判断写成 `code != 0` 正好把 `None` 也算成「没成功」，不用再单独写一条分支。
- 多步的输出用 `[第 1/2 步]` 标出边界；只有一步时（make）不标，那是噪音。
- `cmake` 的两条命令是 `cmake -S <源码目录> -B <构建目录>` 和 `cmake --build <构建目录>`；`make` 只有一条，源码目录就是项目根目录时是裸的 `make`，否则是 `make -C <源码目录>`。
- 命令里的路径**始终相对工具 root**，不是相对源码目录。`source_root=src, build_dir=src/out` 拼出来是 `-B src/out` 而不是 `-B out`——后者会被理解成 `src/out`。「相对谁」混起来是这类工具最容易犯的错，有测试专门钉着。
- `make` 传了 `build_dir` 会被**拒绝**，不是默默忽略：编到哪儿由 Makefile 自己决定，忽略掉的话模型会以为产物就在那个目录里。
- 构建系统也得真的装着，没装就直说「这台机器上没有 cmake」；不查的话模型拿到的是 shell 那句「不是内部或外部命令」，看不出是名字写错了还是根本没装。
- 路径安全这层和 `compile` 共用同一个 `resolve_shell_path()`（在 `tools/paths.py` 里）：先 `resolve_in_root()` 挡住跑出 root 的，再用字符白名单挡住会改变命令意思的。两个工具共用一份规则，不会出现「改紧了一个、另一个还是松的」。除了路径，`build` 没有别的能进命令的自由文本（不像 `compile` 的 flags），所以不需要第二道字符校验。
- `source_root` 的默认值 `.` 归一化之后是 `"."`，过不了字符白名单（它要求首字符是字母数字）。`resolve_shell_path()` 对「解析结果正好就是 root」单独放行——能走到那一步说明 `resolve()` 的结果就是 root，已经没有逃逸可言了。

**MSVC 那条路（7.0 阶段）**

- `cl.exe` 和 `msbuild.exe` 都不在 PATH 上——装了 Visual Studio 也不在。要用它们得先跑一遍 VS 自带的 `vcvars64.bat`，那脚本会把 `PATH` / `INCLUDE` / `LIB` 设好，编译器才知道去哪儿找头文件和库。这件事全在 `tools/vsenv.py` 里。
- 「VS 装没装、装在哪」不靠自己翻硬盘，问 `vswhere.exe`：微软官方的查询工具，装在安装器自己的目录里，位置和 VS 的版本、装在哪都无关。所以这个文件里不出现任何具体的 VS 版本号或安装路径，VS 装几个、装的哪一版由它回答。查询时带 `-requires <VC 组件>` 筛一道——不筛的话，只装了 C# 的 VS 也会被选中，然后才发现里面根本没有 `vcvars64.bat`。
- 取环境要起一次 `cmd` 跑 `vcvars`（这台机器上实测 2.5 秒），所以结果用 `lru_cache` 缓存。一个 `build` 里两步 cmake 也只用一份环境，不是每步各问一遍。失败的结果同样缓存：「这台机器上没有 VS」这个结论一样贵。
- 跑 vcvars 的命令是 `cmd /c "call "<vcvars>" >nul && set"`。`call` 和 `cmd` 是必须的（`.bat` 只有 cmd 能跑）；`>nul` 挡掉 vcvars 自己打的横幅——不挡的话那段横幅会被当成一行环境变量解析进去。
- 解析 `set` 的输出时只切**第一个** `=`：路径里出现等号是常事，切错了整条 `PATH` 就废了。另外名字以 `=` 开头的行要丢掉（`=C:=C:\project` 这种，是 cmd 给每个盘记「当前目录」用的），按第一个 `=` 切出来名字正好是空串——塞进子进程环境里只会添乱。这两条一个是 `KeyError` 逼出来的，一个是测试逼出来的。
- `vsenv` 里所有失败都返回 `None`，从不抛异常。调用方只想知道「VS 能不能用」，找不到就是找不到，不该让整个工具调用炸掉。
- 环境是通过 `subprocess.Popen(env=...)` 传的，**不参与命令字符串的拼接**。所以 `RunCommandTool` 这一版多了个 `env` 参数（`None` = 继承当前环境，也就是原来的行为）——只加了这一个口子，超时、进程树、输出处理一行没动。
- 参数写法：模型一律按 g++ 的写法给（`-std=c++17 -O2 -Wall`），选到 `cl` 时工具翻成 `/std:c++17 /O2 /W4`。**翻不了的直接报错，不猜**——`cl` 碰到不认识的参数只打一句 warning `D9002` 就跳过，然后按缺参数的版本编下去。悄悄按错的编比当场报错糟得多。
- `-std=c++11` 翻成 `/std:c++14`：`cl` 没有 C++11 模式，`c++14` 是它的最低档且向下兼容；不翻的话 `cl` 会忽略掉这个参数（还是那句 `D9002`），模型以为限定了标准、其实没有。
- `cl` 自己带 `/nologo /EHsc /utf-8`，不用模型操心。**`/utf-8` 是实测逼出来的**：`cl` 默认按系统代码页读源码，中文 Windows 上是 936/GBK，UTF-8 的中文源码会被读歪，报出来的是「`C4819` 该文件包含不能在当前代码页中表示的字符」加一句「`C2001` 常量中有换行符」——完全看不出真正的原因是编码。加上它，`cl` 和 `g++` 对同一份源码的理解才一致。
- ⚠️ `cl` 把错误打在**标准输出**里，不是标准错误。`run_command` 两路都收，所以模型照样看得到；但人工排查时别只盯着「标准错误：」那一栏。
- 输出参数的拦截同时认两种写法：`-o` / `--output` / `-MF` / `-MT` / `-MQ` 和 `/Fe:` `/Fo:` `/Fd:` `/Fa:` `/Fi:` `/Fr:` `/Fm:`。和 g++ 那边一样是拒掉而不是忽略。
- `build` 新增的构建系统是 `msbuild`，不是 Ninja / Bazel——`msbuild` 是 VS 自带的，装了 VS 就有，不构成「引入一个新构建系统」。`SYSTEMS` 清单有测试钉死，加第四个得是单独决定的事。
- `msbuild` 构建哪个工程文件是**扫出来的**：先找 `.sln`，没有再看单个 `.vcxproj`。一个都没有、或者有好几个，一律报错让模型自己用 `run_command` 指定——猜错那一个要跑完一整个失败的构建才知道，不如当场问清楚。扫出来的文件名一样要过 `resolve_shell_path()` 这道字符白名单：它是从磁盘上扫来的、不是模型给的，但它一样会拼进命令里，一个带 `&` 的文件名就能把后面的东西变成另一条命令。
- `msbuild` 传 `build_dir` 会被拒绝，理由和 `make` 一样：产物落在哪儿由工程文件自己决定，忽略掉的话模型会以为产物就在那个目录里。

**编译诊断（7.1 阶段）**

- 编译失败时模型最需要的就三件事：哪个文件、第几行、什么问题。三个编译器把这件事写成两种格式——`m2.cpp(3,3): error C2065: ...`（MSVC）和 `m2.cpp:3:3: error: ...`（GCC / Clang）。模型当然看得懂，但它每读一次都要重新认一遍格式，还得自己从一屏文本里把这几行挑出来（cl 一次能喷几十条连带错误）。`tools/diagnostics.py` 把认格式这件事只做一次。
- 诊断的字段是 `file` / `line` / `column` / `level` / `message`，外加一个 `code`（MSVC 的 `C2065`、GCC 的 `-Wunused-variable`）。GCC 把开关挂在消息末尾（`... [-Wunused-variable]`），抽出来当 code，消息里就只剩人话；抽的条件是必须以 `-` 开头——模板诊断末尾的 `[with T = int]` 不是开关，抽走的话消息就断在半句话上。
- **行号直接就是 `read_file` 的行号，不用换算。** 编译器报的行号和 `read_file` / `search_code` 数行号用的是同一套规则（都从 1 开始），解析器切行也直接用 `textfile.split_lines()`——不自己再写一遍切行，就等于不多出一个「行号怎么数」的说法。有测试拿这台机器上真跑出来的 MSVC 输出，配着当时编的那个源文件，验到「报的第 3 行里真的有那个标识符」。
- 列号也是 1 起算的字符位置。有一条测试直接拿 `line[column-1]` 去比：cl 说第 4 行第 11 列，那个位置上真的是它报的那个分号。
- `column` 报不到时是 `None`，不是 `0`——0 是个真实的列号，混起来模型会去第 0 列找。
- `fatal error` 归一成 `error`：它和普通 error 的区别（编译当场停下）已经写在错误码里了（`C1083` 之类），级别上再分一层，调用方就得为它多写一层判断，而判断的结果从来都一样。
- 没有位置的输出不进诊断。链接错误 `main.obj : error LNK2019: 无法解析的外部符号` 就没有行号——诊断是有位置的东西。它不会被丢掉，只是留在「没认出来的」那一堆里，原文照旧呈现给模型。
- **认不出来的行一条都不丢**，原样收在 `Report.other` 里。编译器还会打源文件上下文（`   int x = ;` 加一行 `^`）、`In file included from ...`、命令行回显这些东西，它们有用，只是不是诊断。
- `-Wall` 在 MSVC 那条路上现在会额外带上 `/diagnostics:column`：默认 cl 只报到行（`a.cpp(3): error`），带上之后是 `a.cpp(3,3)`，和 g++ 的 `a.cpp:3:3:` 才对得上。老版本 MSVC 不认这个开关时只会打一句 `D9002` 警告然后忽略，不会因此编不过。
- 解析的是 `run_command` 渲染过的那整段文本，**不分标准输出和标准错误**——因为 cl 把报错打在 stdout、gcc 打在 stderr，而模型要的是「哪儿错了」，不是「它从哪个流来的」。原文两路都在，这条信息没丢。
- 解析器里没有「项目」这个概念：它不认识 root，也不认识任何具体路径。有测试拿同一个文件名配四种目录前缀（相对路径、`/home/...`、`C:\...`）去跑，除了路径字段本身，其余字段必须一模一样。
- 路径里的 `\` 统一换成 `/`，和 `list_files` / `search_code` 返回的写法一致——模型不该先判断「这条路是哪个工具给的」才知道要不要转斜杠。代价是 Unix 上文件名里真有一个反斜杠时会被转错，那种文件几乎不存在，而这个项目跑在 Windows 上。
- 诊断是**另起一段附在原始输出后面**的，前面那段一个字符都没动。编译过了但带 warning 时也附——warning 一样是要改代码才能消掉的。只有 note 时不附：note 说的是「这个标识符是在那儿声明的」，脱离它跟的那条 error 单独看没有意义。
- 一段诊断里混着两种格式是正常的（`make` 串起好几个工具链时就会这样），两种规则不会抢同一行：MSVC 的 `(12)` 那种括号加数字 GCC 那套匹配不了，反过来也一样。
- 模型看到的每一条都渲染成 `文件:行:列: 级别 错误码: 消息`，不管原来是哪家报的——形状一样，行号又挂在前缀里，整行拿去 `read_file` 核对就行。
- 这一版**不做**自动修代码、不做「错误码 → 人话解释」的映射。`build` 那一路在 7.2 阶段接上了同一个解析器。

**构建诊断（7.2 阶段）**

- `build` 的结果末尾同样另附一段诊断，用的是同一个 `tools/diagnostics.py`——没有为构建输出再写一套解析器。构建其实比单文件编译更值得解一遍：一个失败能牵出一串连带错误，而 `msbuild` 一次把整个工程编一遍再一起报。
- 解的是**整段**输出，不按步骤、不按流分开解。构建工具把报错打在哪个流上并不统一（`cl` 打标准输出、`gcc` 打标准错误），而 `run_command` 两路都收下来了、拼在同一段文本里，所以这里不用挑。
- **路径换成本地的**：`msbuild` 报的是绝对路径（命令行里写的是相对的，它自己展开成绝对的），而 `read_file` 只认相对 root 的路径——`C:/...` 里那个冒号连路径白名单都过不了。能对上 root 的换成相对的，对不上的（MSVC 自带的头文件、VS 的 `Microsoft.CppBuild.targets`）原样留着绝对路径：那本来就超出 root，模型读不到，但至少知道问题出在哪儿。换不成相对路径不是错误，不影响其它诊断。
- **说重了的并掉**：`msbuild` 会把每条诊断说两遍——先打在构建日志里，再在结尾的「生成失败」汇总里重复一遍。不去重的话模型会以为真有两处一样的错，条数也是虚的。这**不是**错误折叠：折叠是把连带的错并成一条，这里只是同一行文字原样出现了两次。比的是整条诊断，所以同一个文件同一行上两条不同的错不会并到一起（有测试钉着）。
- **原始输出一个字符不动**，诊断是追加在最后的一段。构建成功但带 warning 时也附——warning 一样要改代码才能消掉。一条诊断都认不出来时（比如工程级错误，见下）不硬凑一段空的，原文照旧。
- 工程级的错误留在「没认出来的」那一堆里（`Report.other`）：`MSBUILD : error MSB1009: 项目文件不存在。` 没有位置可指，诊断是有位置的东西，不能为了凑一条就瞎猜文件行号。反过来 `demo.vcxproj(1,21): error MSB4025: ...` 指的是工程文件自己的第 1 行——那是个真能读的位置，照样解成诊断。
- `msbuild` 在消息末尾挂的那个 ` [D:\...\demo.vcxproj]`（这条是哪个工程报的）原样留在消息里：多工程解决方案里它是有效信息，而位置在行首，不影响模型用。
- 这一步没有碰 timeout、也没有碰进程树处理（那些在 `run_command` 里，7.2 一行没改）；也**不做**错误折叠、不自动改代码——诊断只负责把「哪儿错了」摆清楚。

**改文件（7.3 阶段）**

- `edit_file` 是第一个会改项目文件的工具，所以它真正要保证的不是「能改」，而是「改的**就是**你想改的那一处」。核心就一条：给一段原文，它在文件里必须**正好出现一次**。0 次说明记错了内容，多次说明范围不够——两种都不许猜着改，猜错一次是**静默**的：文件坏了，模型还以为自己成功了。
- 「找到好几处」的报错里会把出现过的行号列出来（`第 1、3 行`），模型据此加几行上下文就能变唯一；报错末尾还会给出另一条路（按行号改）。「一个都没找到」的报错里会提醒「行首的 `12|` 是行号，不要抄进来」——这是模型从 `read_file` 抄原文时最常见的翻车点。
- 行号用的是 `read_file` 那一套：按行改时直接调 `textfile.split_lines()` 数行，不自己再写一遍「行怎么算」。有一条测试拿改完的文件回去问 `read_file`，确认第 3 行真的成了改后的样子。
- **换行是分开算的**：文件里的 `\r\n` 原样保留，但匹配时先把模型给的原文换成这个文件用的那种——模型是从 `read_file` 的输出里抄的，那边 `\r\n` 已经被抹成 `\n` 了，不换算的话 CRLF 文件上一个字都匹配不上，而模型看原文根本看不出差别在哪儿。
- **编码照原样写回去**：读的时候挨个试出来是哪种，写回就用哪种（为此给 `textfile` 加了 `decode_with_encoding()`，只读的工具还用 `decode_text()`）。GBK 的文件按 UTF-8 写回去，整个文件的中文就全毁了。**真踩到的坑**：UTF-8 是拿 `utf-8-sig` 试出来的，而这个编码的**编码器**会自己在开头加 BOM——照它的名字写回去，每个改过的文件都凭空多出三个字节，编辑器看不出来，编译器却把它当成源码的第一个字符。所以没有 BOM 的文件要报 `utf-8`，不是 `utf-8-sig`（`tests/test_edit_file.py` 里有一条专门盯这个）。
- 除了那一处，文件**一个字节都不动**：不重新排版、不动结尾有没有换行、改动之外的每一行都逐字节相同（有几条测试就是整份文件前后对照着比）。
- 写盘走「临时文件 + `os.replace` 原子换名」，临时文件**必须和目标是同一个目录**——丢到系统临时目录去就变成跨卷复制，中间态会露出来。先编码再写，编码表示不了的字符（往 GBK 文件里写 emoji）在动盘之前就被挡下。写到一半失败（磁盘满、被掐）时原文件还在，临时文件也会清掉，不会留下半个文件。
- 路径走的是 `resolve_in_root()`（只读工具那一道），**不是**命令类工具的 `resolve_shell_path()`：这个工具不拼命令，所以那条「文件名里不能有空格、中文」的字符白名单在这里不适用——`my notes.txt` 照样能改。
- 文件有 256 KB 上限（和 `read_file` 一致）和二进制检查：只读到一半就动手，剩下那一半等于没看过，与其改出个半成品不如让模型换别的办法。两个都会被明确说出来，不是默默截断。
- 返回的是一段四个字段摆齐的结果：结果 / 文件 / 位置 / 修改前 / 修改后。再往下一层，改动本身是个 `Change` 数据类（文件、起止行、前后内容、命中几处），渲染出来的那段文字是从它生成的。**失败不走这条**：失败抛 `ToolError`，由执行层统一记成 `success=false` 再把原因回灌给模型——所以模型不会看到一段写着「失败」的结果，它看到的是失败本身。
- 这一步**不做**自动修复循环：改完不自动编译、不自动跑测试、错了不自动回滚。这一阶段只把「可靠地改一处」做扎实；「诊断 → 改 → 再验」那个闭环留到 7.4。

**修改后验证（7.4 阶段）**

- `edit_file` 只保证「改的是你要改的那一处」，不保证「改对了」。改完不验，模型多半会直接宣布修好了——所以 Agent 在每次改动之后自己接着跑一次验证，把结果附在**同一条**编辑结果后面：过没过、原来那条错消失没有、有没有新冒出来的。
- **挑哪个工具**：上次编译/构建/测试跑过的那条命令原样重跑（连 `flags`、构建目录一起）——模型多半是先编译看到错才来改的，只有同一条命令前后才比得出来。没有基线时按文件类型来：Python 走 `run_tests`；C/C++ 从**这个文件所在的那一层往上**找构建文件（`CMakeLists.txt` / `Makefile` / `*.sln` / `*.vcxproj`，就近优先），找到就用 `build`，一个都没有才 `compile` 编它自己。
- **头文件不单独编**：一个头文件编出来的是「没有 main」这类链接错误，不是真问题——拿它当失败会让模型去改本来是对的代码。所以这种情况直接说明白，并给它指条路：「要验证它，请编译一个包含它的源文件（比如上次编过的 `a.cpp`）」。
- 反过来，改的是 `.cpp` 而上次只跑过测试时，**不**拿测试当验证：测试过没过跟这个 `.cpp` 编不编得过是两回事，拿它顶就是**假通过**——那比不验还糟。这时改走 `compile`。
- **怎么比**：认「同一条诊断」只看文件、级别、错误码和消息，**不看行列号**。改完代码行号整段挪位是常事（上面删掉一行，同一条错就从第 5 行变第 4 行），按行列号比会说成「旧的没了、又来一条新的」——两句话都是假的，模型会照着这个结论去查一个并不存在的新问题。
- **过没过是从退出码读的**，不是从「有没有诊断」猜的：命令找不到、链接错误都可能一条结构化诊断都不留。`build` 可能跑两步（cmake 配置 + 编译），任何一步非 0 都算没通过；读不到退出码就不敢说通过。
- 结果里那段「诊断」是 compile / build 自己在末尾附的，比较之前必须先把那段切掉：它是**同一批诊断的另一种写法**（`a.cpp:2:18: error: ...` 会被原样渲染回去），再解一遍就凭空多出一条一模一样的，「已消失 / 仍在 / 新增」全乱（有测试钉着）。
- **验不了的时候也必须说话**：这个 Agent 没装配验证用的工具、改的不是代码文件、改的是头文件——三种都要说清楚「这次改动没有验证过」。什么都不说，模型会当成「没消息就是过了」。验证工具自己没跑起来（比如这台机器没有编译器）说的是「没跑成：……」，和「改错了」是两回事，不能混。
- 认不出结构化诊断又没通过时（比如 msbuild 的「项目文件不存在」没有行列号），把原文节选附上——只给一句「没通过」，模型没法接着查。
- **一轮只验一次**：`agent/verify.py` 自己管的就是「这一次改动验了没」，验完就交回去，它不重试、不循环——「验不过就接着修」是 7.5 接在它上面的另一层（见下）。判断都在 `agent/verify.py` 里，推理循环不认识 `edit_file` / `compile` 这些名字，只是每次工具调用之后问它一句。验证走的是同一个执行层，所以它在 trace 里和模型自己发起的调用长得一样——顺序就是真实顺序，`[Tool] edit_file` 后面那条 `compile` 就是它。
- 真模型端到端跑过一遍（坏的 `main.cpp`）：模型自己 `list_files` → `read_file` → `compile`（`main.cpp:4:10: error C2143`）→ `edit_file` 补上分号，接着**自动**重编一次并附上「验证（compile main.cpp）：通过（退出码 0）／已消失：main.cpp:4:10: error C2143…」，模型的最终回答也照着这段说了「重新编译退出码 0，之前那条 error 已消失」。整个 trace 五条：四条是模型自己调的，第五条是验证。

**自动修复循环（7.5 阶段）**

- 7.4 验完就交回给模型，修不修、怎么修是模型自己的事；模型这时候最常见的动作是**直接宣布修好了**。7.5 补上那一步：验不过就说明还没完，模型想收尾也不行，会被按回去接着修。
- **什么算一轮**：一次 `edit_file` 加上它触发的那次验证。7.5 的版本还要求**先有个坏掉的东西**（没人发现有错、改完验一下也过了就不记轮）；7.8 把这个条件去掉了——改一次就过也是一轮，记成「一轮通过」，见下。
- **催模型（nudge）**：还欠着一次没修好的时候模型给出最终回答，Agent 就追加一条 user 消息把它按回去，把诊断当新情况重讲一遍（还在的错是没解决的、新增的错是新线索、已消失的别再动），然后继续循环。**只催一次**：第二次还是只回话不动手，就停下并把模型自己那句话带进报告——它可能真在说「这个我修不了」，那也该让用户看到。
- **停的规矩**（按检查顺序；7.5 定了四条，7.6 又加了「同一次改动又做了一遍」）：改完文件一个字节没变（sha256 指纹相同——`edit_file` 把原文原样替换进去时也会报成功，文件真被重写了一遍但内容没变，这么转下去只是把同一个错误重放）；连着两轮诊断**完全相同**（认的是「同一条」，不看行列号，用的是 7.4 那个 `compare()`）；用满 `max_repair_rounds`；修复期间 `edit_file` 没改成（原文没找到、命中多处——文件一个字节没动，属于「这一轮什么也没发生」）。加上正面的那条：验证通过就结束，模型正常给最终回答。
- **`max_repair_rounds` 和 `max_steps` 是两个预算**：一个管「最多修几轮」（默认 5），一个管「一次 `run()` 最多问几次模型」（默认 15）。轮次不该拿步数凑——步数里还混着读文件、搜代码这些根本不算修的调用。**真踩到的坑**：步数用完而修复还没结束时，7.0 的 `AgentError` 会把整轮对话回滚掉——那等于把刚改好的代码连同历史一起扔了。所以这条路上不再抛异常，而是收个尾把报告出去（代码留在盘上、历史留着）。
- **不回滚**：停下就是停下，代码保留最后一次修改后的样子，不自动回滚、也不再自动改一次。要接着修，下一轮对话里模型看着完整历史继续就是了。「自动改坏了再自动改回去」是另一个能力（要能判断「改回去」是对的），这一阶段不做。
- **模型看到的新诊断是 7.4 那一段**：验证结果里的「已消失 / 仍在 / 新增」，本来就是照着「和上一次验证比」算的。这一层不重新解析任何文本——判断用的全是 `Verifier` 留下的结构化结果（`agent/verify.py` 里的 `Verification`），所以永远不会把渲染出来的诊断块再解一遍（那会凭空多出一条一模一样的）。
- **判断和执行是分开的**：`RepairLoop` 一行命令都不拼、不直接碰工具，只回答 Agent 两个问题——「这次工具调用之后要不要记一轮、要不要停」和「现在能收尾吗」。工具照旧全走 `ToolExecutor`，所以修复过程在 trace 里和模型自己发起的调用一模一样，顺序就是真实顺序。
- **没触发自动修复时行为一点没变**：没欠着修复的时候，这一层不会拦住模型（普通问答、只读工具调用走的还是 7.4 那条路）。改完就过的一次修改现在会记一轮、多一句「第 1 轮通过」的回执（7.8 起），但那只是报个信，不是把它按回去接着修。
- 真模型 + 真 `cl.exe` 端到端跑过一遍**两轮**的：文件里埋了两个错，第二个错**第一遍根本看不见**——`#include "mising.h"` 是**致命错误**（C1083），它后面的代码压根没编到，所以照抄编译器输出是修不完的。模型 `read_file` → `compile`（只看到 C1083）→ 删掉那行 include → **自动**重编 → 验不过，附上「已消失：C1083／新增：`totl` 未声明的标识符 C2065」→ 模型接着改成 `total` → 自动重编退出码 0 → 第 2 轮通过，报告「自动修复：第 2 轮通过（compile main.cpp），修复结束」。整个 trace 七条，两次验证都是自动的。

**两关验证与修改指纹（7.6 阶段）**

- 7.5 的「修好了」看的是编译那一关。编得过不等于对：`return a - b` 编得干干净净，测试一跑就是红的。7.6 把成功标准换成 `Verification.ok` ——**主验证过了，该跑的测试也得过**（`passed and (tests is None or tests.passed)`）。编译通过只说明编译这一关过了。
- **两关怎么串起来的**：都在 `Verifier.check()` 里，模型不用做任何额外动作。主验证跑完（C/C++ 是 `compile` / `build`，Python 直接就是 `run_tests`），如果主验证是编译 / 构建**并且过了**，就在同一个执行层接着发一次 `run_tests`，把结果追加在同一段验证文字后面。Python 的改动本来跑的 `run_tests` 就是终局，没有第二关。
- **测试那一关不当下一次比较的基线**：`self._last` 保持是编译那次，编译诊断的「已消失 / 仍在 / 新增」链条不被测试结果顶掉；测试结果用 `dataclasses.replace` 挂到 `self.last.tests` 上，谁要用谁去取。
- **没有测试的项目不能算失败**：`run_tests` 跑的是 `python -m unittest discover -s tests -t .`，`tests/` 得是个可导入的包（有 `__init__.py`），不然它自己会报「Start directory is not importable」退出 1。把这种假失败喂进修复循环，模型会去修一个根本不存在的问题。所以先用 `_has_tests()` 探一下，不是包就明确写「这个项目里没有能跑的测试，这一关跳过——这次改动只以编译 / 构建为准」（还是 7.4 那条：验不了也得说话）。
- **测试失败了模型看得到原文**：验证块里写「测试（run_tests）：没通过（退出码 1）」，后面跟着输出节选，模型照着它接着改——和编译诊断一样，是同一条工具消息里附回来的，不用另开一轮。
- **修改指纹**：每轮 `edit_file` 记一个 sha256，内容是「文件路径 + 改动位置 + 换上去的新内容」（换行先统一成 `\n`，免得 CRLF / LF 两种写法算出两个指纹），显示时取前 8 位。位置从 `edit_file` 渲染结果里的「位置：」那一行拿——那里写的是「第 5 行（原文替换，命中 1 处）」这种，正好是「动了哪儿」。
- **重复指纹就停**：同一个指纹第二次出现，说明模型把刚改掉的东西又改回去了（A 改成 B、下一轮又改回 A），这时报「检测到重复修改（同一个地方又改成一样的内容），停止继续尝试」并结束修复。**只有指纹重复才触发**——同一个文件连着改很多次不算，只要每次动的地方 / 内容不同，就正常接着修（有一条测试专门钉着这个：同一个文件里改两处不同代码，两轮都照走）。
- **`RepairRound` 现在把两关的结果都记下来**：轮次、文件、改了什么、指纹、用哪条命令验的、退出码、诊断对比、编译过没过、测试的文本 / 过没过 / 退出码，还有一个算出来的状态。`as_line()` 一行就能摊开：`第 1 轮 · main.cpp 第 5 行（原文替换，命中 1 处） → compile main.cpp 退出码 0 通过；run_tests 没通过（退出码 1） · 指纹 bd91c229`。
- **测试也算「原地打转」**：连着两轮看到的完全一样这条规则，现在编译诊断和测试输出都认。测试输出先做个签名——unittest 结尾那行「Ran 2 tests in 0.001s」每次都不同，签名前先把它切掉，不然这条规则永远触发不了（真踩到的坑）。卡在测试上时催模型的话术也跟着变（「卡在测试上」）。
- **Repair Summary**：收尾时 `Agent._finish()` 把 `repair.summary()` 加在最终回答前面，并且这段拼好的文字会**写回** `message["content"]`——历史里存的和用户看到的是同一段。形如「修复 2 轮；第 1 轮编译没过；第 2 轮编译通过、测试通过；最终成功。」每轮的状态是四种之一：编译没过 / 测试没过 / 编译通过 / 编译通过、测试通过。一次都没修过（没有修复轮）就不加这句，回答和以前一模一样。
- **提示词也跟着改了口径**：告诉模型「编译通过只说明编得过，逻辑写错了照样编得过，测试红着不算修好，测试输出就在同一条消息里」，停的原因里也加上了「同一处改来改去」。
- **Trace 里能看到两关**：测试那一关走的是同一个 `ToolExecutor`，所以 `[Tool] edit_file` 后面紧跟两条自动调用——先是 `compile`，再是 `run_tests`。`max_repair_rounds` 和 `max_steps` 依旧是两个独立预算，「不自动回滚」也照旧。
- 真 `cl.exe` + 真 `run_tests` 的端到端（`RealTwoStageTest`）：`add(a, b)` 写成 `a - b` 的 `main.cpp`（编得过，测试断言输出是 `5` 所以红）→ 第 1 轮编译通过、测试没过 → 模型接着改成 `a + b` → 第 2 轮两关全过；trace 断言就是 `[COMPILE, EDIT, COMPILE, RUN_TESTS, EDIT, COMPILE, RUN_TESTS]`。真 DeepSeek 也端到端跑过一遍：模型一次 `edit_file` 把缺分号和 `a - b` 一起改掉，`compile` 和随后的 `run_tests` 都是自动跑的，两关都过。

**修复记录落盘（7.7 阶段）**

- **只记，不判断**：`agent/history.py` 不认识工具、不参与任何决定，`RepairLoop` 也不知道有它——记录直接在 `run()` 跑完之后单独写一次，读的全是已经算好的东西（`rounds`、`stopped`、`pending`、`summary()`），一个字都不重算。所以报告里怎么说的、摘要里怎么写的、JSON 里怎么记的，三处永远一致。判断的代码和记录的代码不在一处，改一个不会碰坏另一个。
- **写到哪儿**：默认是项目根目录下的 `repair_history/`，目录不存在会自己建。想换地方就 `Agent(history=RepairHistory(directory=...))`。`main.py` 已经装上（所以命令行每轮对话都会留一份）；测试里不装——不然跑一次测试套件就往仓库里塞几百个文件。**没装就是不记**，其余行为一个字都不变。
- **什么时候记**：`run()` 正常跑完记一次。中途抛异常（LLM 调用失败、工具轮数超限之外的那种失败）那一轮本来就整个回滚了，没有「结果」可记。**没改过代码也记**（就是普通问答、只读工具调用），只是 `round_count` 是 0、`rounds` 是空的——留一笔「这轮没干活」，不伪造轮次。改过代码的那些轮次一律记（7.8 起，改一次就过也是一轮）。
- **一份记录长什么样**（下面这份是真跑出来的，删掉了临时项目路径无关的部分）：

```json
{
  "time": "2026-10-01T21:33:16+08:00",
  "request": "main.cpp 编译不过，先跑一次 compile 看看错在哪；改好之后编译和测试都要过（add(2,3) 应该打出来是 5）。",
  "status": "修好了",
  "fixed_round": 1,
  "stopped": null,
  "summary": "修复 1 轮；第 1 轮编译通过、测试通过；最终成功。",
  "round_count": 1,
  "rounds": [
    {
      "round": 1,
      "file": "main.cpp",
      "edit": "第 4–5 行（原文替换，命中 1 处）",
      "fingerprint": "22401141",
      "state": "编译通过、测试通过",
      "compile": { "command": "compile main.cpp", "passed": true, "exit_code": 0 },
      "diagnostics": {
        "gone": ["main.cpp:5:1: error C2143: 语法错误: 缺少“;”(在“}”的前面)"],
        "still": [],
        "added": []
      },
      "test": { "passed": true, "exit_code": 0, "detail": "run_tests 通过（退出码 0）" }
    }
  ]
}
```

- **这份记录是干什么用的**：同一个错误反复出现时能翻旧账（哪次改的、改成什么、当时测试红在哪一行）；`round_count` 一直往上走的项目，说明那个地方模型总也修不好，值得人去看一眼。改一次就过的那种也记着（`state` 是「一轮通过」），所以一次 run 到底动过没有、动了几处，翻记录是看得全的。
- **`status` 三种**：`没修`（一次修复轮都没有）、`修好了`、`没修好`（停了，或者还欠着一次没验过的修改）。看的是「有没有修复轮、停没停」，**不是模型说自己修好了没有**。`stopped` 就是 7.5/7.6 那条停下来的原因原文，`null` 表示没停。旁边的 `fixed_round` 是**第几轮修好的**（7.9 加的，从 `rounds` 推出来的，不重跑任何验证）：一串失败轮里只认最后真正成功的那一轮，没修好或者压根没改代码就是 `null`——有值一定对应 `status: "修好了"`。
- **文件名**：`20261001-213316-c804ce.json`——时间打头（人一眼看出先后）+ 6 位随机数（机器保证不重名）。同一秒里连跑两次，时间那截一样，随机那截不一样，所以**不会覆盖**；真撞上了（随机也撞车）就再抽一个。
- **落盘和 `edit_file` 用同一套**：先在同目录写临时文件、`flush` + `fsync`、再 `os.replace` 原子换名。半截 JSON 比没有更糟——翻的时候解不开，还不知道是这次没记上还是文件本来就这样。有测试盯着「跑完之后目录里只有 `.json`，没有半个 `.tmp`」。
- **写失败不算失败**：`record()` 里 `except Exception` 兜住一切（连 json 序列化自爆都算），原因写进 `last_error`，`last_path` 是 `None`，返回 `None`。`run()` 那边**连 `try` 都不用写**——因为这个函数绝不外抛。命令行会在 stderr 打一行 `[历史记录] 这次修复记录没能写进 ……`，让人知道「翻不到记录」不是「这段时间没修过东西」。有一条测试专门把目录位置用一个同名文件占住，确认这种情况下回答照给、修复结果照旧。
- **「一轮通过」是怎么来的（7.8）**：7.7 真跑的时候发现，模型**不看编译结果直接改好**（先 `read_file` 就 `edit_file`）的那一次，记录里是 `round_count: 0 / status: "没修"`——当时的「修复轮」要求先见过坏状态，没先编译就等于没见过。7.8 把这个条件去掉了：**一次 `edit_file` 加上它触发的那次验证就是一轮**，改完第一次验就过的记成 `state: "一轮通过"`（`RepairRound.one_shot` 这个标记，摘要里念「第 1 轮就通过」——不然「第 1 轮一轮通过」读着别扭）。先坏后修的那种一个字没变。上面那份示例记录是「先编译看到错、再改」的，所以 `state` 还是「编译通过、测试通过」。


**项目文件索引（8.1 阶段）**

- **职责只有一个**：看清项目里有什么。后面的 Symbol Index（每个文件有哪些类 / 函数）、Code Chunk（按结构切块）、Hybrid Search、Code RAG 都从这份清单上接着做。所以本阶段**不存文件内容**——切块的时候再按路径去读，读到的还是不是索引当时那份，由 `digest` 回答。没有 embedding、没有向量库、没有语义搜索，也没有把索引接进 Agent：现有行为一个字没动。
- **一条记录（`index/project.py` 的 `IndexedFile`，冻结的 dataclass）**：`path`（相对项目根、`/` 分隔，和 `list_files` 一致）、`language`（语言 id，见下）、`status`、`size`（字节）、`mtime`（`st_mtime` 原值，拿来比较、不格式化）、`digest`（内容 sha256 前 16 位，只有收进来的才有）。
- **状态四种，跳过的也留一条**：`indexed`（文本，收进索引）、`binary`（二进制，或 UTF-16 这类两种编码都解不开的）、`too_large`（超过 `max_file_bytes`，默认 1 MB，不读内容）、`unreadable`（stat 或读的时候失败：被占用、扫到一半被删）。翻记录时看得到「这个文件我见过、没收，因为 X」，而不是凭空消失；`files()` 只给 `indexed` 的——后面的阶段该读哪个，看它。（本项目的 66 条记录里有一条 `binary`：`电脑磁盘 (D).lnk`，Windows 快捷方式带 NUL 字节。）
- **只扫 root 以内，规则只有一份**：root 过 `tools/paths.py` 的 `check_root`（磁盘根、系统目录、不存在都在这儿被挡），目录遍历走 `tools/tree.py` 的 `iter_files`——和 `list_files` / `search_code` 是**同一个函数**，所以「跳过 .git、node_modules、build」不另立一套，也不可能出现「`list_files` 看不见、索引却扫到了」的文件。有一条测试把两边的文件集合直接对起来看。
- **「是不是文本」也是同一套判断**：`read_bytes` + `decode_text`（`utf-8-sig` → `gbk`，含 NUL 就拒），和 `read_file` / `search_code` 一致——`read_file` 读不了的文件，索引也不收。单个文件读不动不中断整次扫描（记一条 `unreadable` 接着扫），和 `search_code` 跳过坏文件是同一条规矩。
- **语言识别就是一张表**：`index/languages.py` 的 `LANGUAGE_BY_SUFFIX`，id 用小写短名。现在能抽结构的只有 Python 和 C/C++（C 和 C++ 合成 `cpp` 一门：提取器本来就不分，`tools/cpp.py` 一套吃两种）；Java / Go / Rust / JS / TS 只是**认得出名字**，索引照记，等 Symbol Index / Code Chunk 阶段给它们补提取器。加一门语言，第一步就是往这张表里加后缀。
- **怎么用**：`index = ProjectIndex()`（默认整个项目，也能 `root=` 指到别处）→ `index.build()` → `index.entries`（全部记录）/ `index.files("python")`（只看已索引的，可再按语言筛）。改了、加了、删了之后再 `build()` 一次就是刷新——**全量重建**，不留旧账；本阶段不做增量，但每条记录上的 `size` / `mtime` / `digest` 就是以后做增量要比的三个数。构造和扫描全程**只读**：不建文件、不改文件，有测试对着「扫完之后每个文件的大小和修改时间一个都没变」。
- **为什么摘要必须有**：光看 `mtime` 不够稳——有些文件系统的时间戳只精确到秒，同一秒里改两次看不出来。摘要也是以后给切好的块做缓存、判断「这份内容切过没有」的依据。
- 语言识别、忽略目录、二进制 / 超大 / 读不动的判定、root 边界、刷新（新增 / 删除 / 改内容）各有测试；另外拿本项目真扫了一次：70 条记录、再扫一遍逐条相同。

**符号索引（8.2 阶段）**

- **职责**：在文件清单之上回答「每个文件里有什么」。每个符号一条记录，给后面的 Code Chunk（按符号边界切块）和 Hybrid Search（按名字 / 类型找）当底子。仍然**不是工具、不进 Agent**——Agent / RepairLoop / Verifier / 编译测试 / `edit_file` 一个字没动；也没有 embedding、向量库、语义搜索、切块。
- **一条记录（`index/symbols.py` 的 `Symbol`，冻结的 dataclass）**：`name`（简单名，`draw`）、`kind`（`class` / `struct` / `function` / `method` 四种）、`path`（相对项目根，和 `list_files` 一致）、`start_line` / `end_line`（1 起、闭区间，能原样拿去 `read_file` 切出这个符号）、`digest`（**所属文件**的内容摘要，不是符号自己的——文件一改，这条就作废）、`parent`（父级符号的限定名，顶层是 `None`；语言之间统一用点连接）。`qualified` 属性拼出 `Agent.Inner.run`，查名字时简单名和限定名都认。
- **行号是要拿去切代码的**：Python 直接用 `ast` 的行号（带装饰器的定义**从装饰器那一行**算起，切块才不会把 `@app.route(...)` 切掉）；C/C++ 用 `tools/cpp.py` 新增的 `spans()` 扫出来的行范围——`template <...>` 和返回类型单独占行时算进去，`public:` 这类访问修饰符不算（它和后面的声明会粘成一段，`Span.start` 会跳过它）。`extract()` 的输出一个字节没变，`code_summary` 不受影响。
- **解析只有一份实现**：Python 走新的 `tools/pyast.py`（把 `code_summary` 里的 AST 走法抽出来，装饰器、`try/except`、`match/case` 的走法都在那儿），C/C++ 走 `tools/cpp.py`——`code_summary` 和符号索引认的是同两套，不会各说各话。
- **不产生过期符号**：读回来的内容先核对 `digest`。对不上（文件被改过、或者刚长大）就整个跳过、记一条 `Skipped(changed)`，而不是拿旧行号去切新文件。文件没了、读不动是 `unreadable`；Python 语法错是 `unparsable`。这三种之外的（`.md`、或者 Java / Go 这些还没有提取器的语言）**不算跳过**——那不是出错，是还没轮到。
- **C/C++ 的方法 / 函数是近似的**（`cpp.py` 本来就是逐行扫的近似结果）：类体里的函数算方法；名字带 `::` 限定的也算方法，因为带限定的定义绝大多数是成员函数——`void app::run() {}`（命名空间里的自由函数）会被认成方法，这是已知偏差；转换运算符（`operator std::string`）的名字不拆，模板实参（`Box<int>::put`）会让限定名认不出来。union / enum / namespace 现在只参与父级链、不产出符号，要加就是往 `_SYMBOL_KIND` 里补一行。
- **怎么用**：`index = SymbolIndex()`（默认整个项目，也能 `root=` 指到别处）→ `index.build()` → `index.symbols(path=..., name=..., kind=...)` 按条件查（条件是「与」的关系，都不给就是全部；结果按文件路径、文件内出现顺序排），`index.skipped` 看谁没进来、为什么。`root=` 那份文件清单每次 `build()` 都是全量刷新；`project=` 传进来的那份归调用方管（这样才留得出「清单建好之后文件又改了」的场景，digest 保护才有真事可做）。
- 测试：Python 的 class / function / method / async、C/C++ 的四类、嵌套符号与父级链、行号（拿真源文件切出来验，不是只比数字）、装饰器与 template 的起点、`digest` 进入记录、文件改过 / 删掉 / 语法错 / 未知语言、查询、只读（建索引前后每个文件的大小和修改时间一个都没变）。另外拿本项目真建了一次：**2174 条符号**（61 个文件，327 个类、175 个函数、1672 个方法——方法多是因为测试文件里全是 `def test_...`），一条都没跳过。

**代码块（8.3 阶段）**

- **职责**：前两层只记「哪儿有什么」，这一步才把**代码正文**取出来。一个类 / 函数 / 方法一段，边界就是符号的行范围，后面的 Hybrid Search / Code RAG 检索这些块；Agent 也能顺着 `path` + `start_line` / `end_line` 用 `read_file` 回去看原文。仍然**不是工具、不进 Agent**——Agent / RepairLoop / Verifier / 编译测试 / `edit_file` 一个字没动；也没有 embedding、向量库、语义搜索。
- **一条记录（`index/chunks.py` 的 `CodeChunk`，冻结的 dataclass）**：`path` / `start_line` / `end_line`（1 起、闭区间、`/` 分隔，原样就能交给 `read_file` 复核）、`symbol`（**限定名**，`Agent.run`）、`kind`（class / struct / function / method）、`language`、`digest`（**所属文件**的摘要，不是这段代码自己的）、`parent`（父级符号的限定名，顶层是 `None`）、`code`（正文）。`id` 属性拼出 `agent/agent.py:Agent.run:40-52`——可读的拼法，翻日志时一眼知道说的是哪段代码。
- **正文是真读出来的**：按行号从文件里切，切出来的和 `read_file` 显示的那几行逐字节一致（只是没有 `42|` 那样的行号前缀，换行统一成 `\n`）。不拿符号名或摘要拼一段出来——拼出来的东西看着像代码，实际查不到、对不上，比没有更糟。有一条集成测试把全项目每条 chunk 的正文和源文件逐字节对一遍。
- **不产生过期 chunk**：读文件走的是 `SymbolIndex.read_verified`——和符号索引**同一份实现**（先核 `digest` 再解码），digest 对不上就整段不切，记一条 `Skipped(changed)`。行号错了的 chunk 比没有 chunk 更糟：检索命中之后，Agent 会照着它去 `read_file` 看一段完全不相干的代码。
- **一个 symbol 一条 chunk，嵌套保留成父子**：类里套方法时两条 chunk 的行范围本来就不同（类的更大、正文里含着方法），这是有意保留的两种粒度——`parent` 字段把 `Class.method` 的关系挂着，`chunks(parent="Agent")` 就能取到下一层。只有行范围**一模一样**时才丢掉一条（一行写完的 `struct A { void f(); };`：内层切出来的代码会和外层一个字不差），只留外层。去重按「同一文件 + 同一段行」判，不按正文——两个类里各有一个写法和名字都一样的方法，代码相同、位置不同，那本来就是两条。
- **没有 symbol 的文件本阶段不切**：`.md`、`.json`、还没有提取器的 Java / Go 这些，一条 chunk 都不产，也**不算跳过**（不是出错，是还没轮到）。扩展点只有一处——`build()` 里那个 `continue` 上面的注释写清了以后按行窗口切这类文件该从哪儿接；现在刻意不做：为覆盖所有文件设计一套 fallback，会把「按 symbol 边界切」这条主线冲淡，切出来的边界也说不清是什么。
- **怎么用**：`index = ChunkIndex()`（默认整个项目，也能 `root=` 指到别处）→ `index.build()` → `index.chunks(path=..., symbol=..., kind=..., parent=...)` 按条件查（条件是「与」；`symbol` 简单名 / 限定名都认），`index.skipped` 看谁想切却没切成、为什么。符号索引由谁管的规矩和 8.2 一样：`root=` 自己管、每次 `build()` 全量刷新；`symbols=` 传来的归调用方管（这样才留得出「索引建好之后文件又改了」的场景）。
- 测试：Python / C++ 的符号 → chunk、正文逐字节对源文件、行号、装饰器与 template 的起点、`digest` 校验、文件改过 / 删掉、嵌套父子、一行写完的重复去重、空文件与无符号文件、查询、只读。另外拿本项目真切了一次：**2174 条 chunk**（61 个文件，327 个类、175 个函数、1672 个方法），一条都没跳过，也没有触发去重规则（这个项目里没有 C/C++ 源码）。

**检索（8.4 阶段）**

- **职责**：前三层是「建」，这一步是第一个「查」——给一句查询字符串，在**现成的 chunk** 上找出最像的那些，排好序返回。仍然**不是工具、不进 Agent**——Agent / RepairLoop / Verifier / 编译测试 / `edit_file` 一个字没动；也没有 embedding、向量库、语义搜索。它不重扫源码、不重解析、不重切块：进来的是 `ChunkIndex`，检索只读不写（要刷新得自己调 `index.build()`，有一条测试盯着「建好索引之后往磁盘加文件，检索看不见它」）。
- **一条结果（`index/retrieval.py` 的 `SearchResult`，冻结的 dataclass）**：`chunk`（命中的那条 `CodeChunk`）、`score`（总分，就是下面各项之和）、`matches`（**为什么命中**：`Match(kind, detail, score)` 的元组，可能不止一条）。`reason` 属性把它拼成一句话给人 / 给模型看：`限定名 SymbolIndex.build（+100）；正文里的 build（+6）`。`Match.kind` 是英文短 id：`symbol` / `path` / `code`（以后 embedding 那条用 `embedding`）。
- **四种匹配，都带「为什么」**：symbol 简单名（`run`）、qualified symbol（`Agent.run`）、文件路径（`agent/agent.py`、`client.py`、`llm`）、chunk 正文关键词（含中文——注释和文档字符串也搜得到）。查询先拆一次（`Query`：原文、剥掉首尾标点并小写、词表），`Agent.run()` 和 `Agent.run` 是一回事。名字会再拆成词：查 `repair` 命中 `max_repair_rounds`，查 `ask` 命中 `Agent._ask`。
- **分数是一张表（`index/retrieval.py` 顶部）**：整名 100 / 简单名 80 / 整条路径 70 / 文件名 60 / 整句正文 40 / 目录名 40 / 名字里的词 30 / 名字的一部分 15 / 路径里出现 12 / 正文里出现 6。分档的道理只有一个：**名字上的命中比正文里的命中可信**——查 `run`，名字就叫 `run` 的那个必须排在「正文里恰好出现过 run」的前面（这条有测试钉着）。数值是拍的，要调只动这一处。（8.7 又加了一档 +10：正文命中落在 function / method 上的粒度奖励，见下。）
- **同一条查询，顺序永远一样**：分数相同时按 路径 → 起始行 → 符号名 排（`_order()`），没有随机、没有字典序依赖，`top_k` 截出来的也就是同一批（8.7 起整名命中单独排最前，见 8.7）。`top_k` 默认 10；`None` 是不限；**0 或负数是一条都不给**（不是「倒数几条」）。查不到、空查询、只有标点的查询，都老老实实返回空——宁可少给，不给凑数的。
- **打分可以整个换掉（这是给 embedding 留的口）**：`scorers` 是一串 `(Query, CodeChunk) -> list[Match]` 的函数，默认三个（符号 / 路径 / 正文）。`Retriever(index=..., scorers=DEFAULT_SCORERS + (你的打分器,))` 就能加一个——语义打分对**每个** chunk 都给一条 `Match("embedding", ..., 相似度 × 权重)`，排序、去重、`top_k` 一行都不用改（每个 scorer 对每个 chunk 都会被问一遍，有测试盯着这条）。测试里用一个「假装的 embedding 打分器」把默认打分器找不到的 chunk 捞到了第一位，证明这个口是通的。
- **两个小坑，各有测试钉着**：①（8.3 起就有的规矩）`search()` 发现索引**从没建过**会先替它建一次——「只想搜一句、不想管索引」是正常用法，不该静默返回空；建过的（哪怕已经过时）不碰。②模糊扫描（在正文 / 路径里**找子串**）有长度门槛：纯英文 3 个字符起，汉字 2 个就够。不然查 `agent/agent.py` 里的 `py` 会把全项目每个 `.py` 都算一条命中。精确匹配（整名、文件名、目录名、名字里的整词）不受这条管，短词照样能精确命中。
- **怎么用**：`retriever = Retriever()`（默认整个项目，也能 `root=` 指到别处、`index=` 传一份自己的）→ `retriever.search("max_repair_rounds")` / `search("重试", top_k=5)`。每条结果顺着 `chunk.path` + `start_line` / `end_line` 就能用 `read_file` 回去看原文——检索给的是「哪儿有」，不是「答案」。
- 测试：符号精确 / 限定 / 部分 / 名字里的词、文件名 / 词干 / 目录名 / 整条路径、正文关键词（含中文）、多结果排序、同分顺序跑两遍一致、`top_k`（1 / 2 / 0 / 负数 / 超量 / 默认 10）、空查询与只有标点的查询、特殊字符（`Agent.run()`、引号、多余空白）、分数等于各项之和、自定义打分器与整体替换、索引的懒建与不重扫、只读。另外拿本项目真查了一轮：**2260 条 chunk**（比 8.3 时多 86 条：`retrieval.py` 和它的测试文件贡献 85 条，`chunks.py` 里为懒建补的 `built` 属性 1 条），`ProjectIndex` / `SymbolIndex.build` / `run_command.py` / `repair` / `超时` 这些查询头一条都落在该落的 chunk 上，平均一次查询 **~18 ms**（全量扫一遍 2260 条；现在没做任何索引加速——真嫌慢，第一步是别每次重新 `lower()` 一遍正文，或者给词建个倒排表，那是后面的事）。
- **下面可以接的**（都还没做）：embedding / 向量库这条（`scorers` 的口已经留好）；把检索包成一个 `search_code_chunks` 工具给 Agent 用；正文的倒排索引（现在是线性扫）；结果里带上 `parent` / 类的上下文；多轮查询改写。**顺序上先别急着上 embedding**：先用现在这套跑几个真问题，看看到底是「关键词找不着」还是「找着了但排序不对」——前者才是 embedding 能解决的，后者多半是权重表的事。

**检索评估（8.5 阶段）**

- **为什么要有这一层**：8.4 的检索好不好，之前只能翻几条结果「感觉还行」。感觉没法比较——以后调权重、加 embedding，凭什么说新的比旧的强？`Evaluator` 拿一组**手写 case**（一句查询 + 期望命中的目标）挨条喂给 `Retriever`，看目标落在第几名，汇总成 Hit@1 / Hit@3 / Hit@5 和平均耗时。它只回答一个问题：**给一组已知答案的查询，检索把答案排到了第几名。** 这层**只调用** `Retriever.search()` 这个公开入口——打分规则、排序逻辑、索引一个字没动，Agent / RepairLoop / Verifier / tools 也没动；没有 embedding、向量库、自动生成测试问题、Agent Tool。
- **一条 case（`EvaluationCase`，冻结 dataclass）**：`query`（喂给检索的那句话）、`expected_path` / `expected_symbol`（期望命中的目标，可只给一个，也可都给——都给就是「必须同时满足」；symbol 简单名 `build` 和限定名 `ChunkIndex.build` 都认）、`expected_nothing`（**反例**：这条查询本来就该查不到，查到反而算错；和上面两个只能给一边）、`scenario` / `note`（给人看的短标签和说明；以后要加字段比如难度、来源，从这儿加，不动评估逻辑）。构造时就把写错的挡掉：空 query、一边给 `expected_nothing` 一边又给期望目标、什么都没给，都直接报错。
- **一条结果（`EvaluationResult`）**：`case`、`results`（前 `top_k` 条 `SearchResult`）、`rank`（**第几名命中**，1 起；`None` = 前 `top_k` 里没有）、`elapsed_time`（这一条花了多少秒）。`hit1` / `hit3` / `hit5` 是从 `rank` **现推**的属性，不是另存一份数——不会出现「明细说命中、汇总说没中」。
- **指标怎么算（`EvaluationReport`）**：Hit@1 / Hit@3 / Hit@5 **只统计「该找到」的 case**——本来就查不到的查询（反例）混进命中率里只会把分数搅浑，它们是另一类，单独统计「确实没查到几条」。平均耗时是所有 case 一起算（反例也是一次真查询）。评估器本身不去重——给它两条一样的 case，它就真跑两遍、算两条；自带那份 case 里 query 不重复，有测试拦着。`summary()` 直接把逐条裁决 + 总账拼成一段文本，汉字按显示宽度补空格，中文查询不会把后面的列顶歪。
- **建索引不算检索耗时**：第一次 `search()` 会顺手把索引建起来（8.4 的懒建规矩），那一两秒混进 `elapsed_time` 就是假数据。评估开始前先建好，计时只包住 `search()` 本身。
- **case 存 JSON 不写在 py 里**（`index/evaluation_cases.json`）：这个项目**把自己也索引了**。case 写成 Python 常量，那些查询字符串就会跟着模块的 chunk 一起进索引——等于把答案提前埋进考卷（8.4 的真项目测试就踩过这个坑，同一条查询命中了测试文件自己）。JSON 没有符号、不产 chunk，天生干净。加载器对字段名和类型很严：不认识的字段、类型写错、少 `query`、文件不是 JSON、最外层不是数组、文件读不到——全部直接报错，不静默忽略。**写错的期望等于那条 case 永远不命中**，看起来像「检索不行」，其实是 case 写错了。
- **自带 9 条 case，覆盖七类场景**（`scenario` 就是这些标签）：文件名（`retrieval.py` → `index/retrieval.py`，第 1）、symbol 限定名（`ChunkIndex.build`，第 1）、类（`ProjectIndex`，第 1）、函数（`digest_of`，第 1）、功能描述两条（「把文件读回来」→ `SymbolIndex.read_verified`，第 2；「校验文件有没有被改过」→ 同一个函数，**一条都没查到**——这是故意留的，见下）、代码关键词（`fsync` → `agent/history.py` 的 `RepairHistory._write`，第 2）、反例两条（`量子纠缠`、`missing_symbol_zzz`，都确实没查到）。几条刻意用的是**人话**而不是符号名——评估要测的是用户真会怎么问。
- **当前基线（真跑，2358 条 chunk）**：**Hit@1 4/7、Hit@3 6/7、Hit@5 6/7**，两条反例都查得到「查不到」，平均 **~18 ms**（只算检索）。这个数字现在告诉我们三件事：① 名字类查询（文件名、限定符号、类、函数）全在第 1 名——字面匹配最擅长的就是「你叫得出名字」；② 两条落在第 2 名的，都是**答案被它自己的类挡住**：类 chunk 的正文里含着方法体的注释（类的那段代码包含方法），分数和方法的 chunk 咬得很近，排序把类排在了前面——这是当前打分最明显的短板；③ 真·描述查询「校验文件有没有被改过」一条都没查到，因为这句话里没有一个词出现在代码里——**这正是 embedding 要解决的，也是这次评估最有价值的一条：它给了 embedding 一个明确的、可量化的靶子。**
- **加了 embedding 之后怎么比**：同一组 case、同一个 `Evaluator`，只换 `Retriever` 的 `scorers`（8.4 留的口），前后各跑一遍，对着三样东西看：Hit@1/3/5 涨没涨；那两条 description case 有没有从「第 2 名 / 一条没有」变成第 1；平均耗时涨了多少（embedding 要算相似度，这是要付的代价）。case 集可以随项目长大，但**比较时必须用同一份**——换了题再比分数，数字没有可比性。
- **怎么用**：`python -m index` 在真项目上跑一遍自带 case 集（入口在 `index/__main__.py`，不放在 `evaluation.py` 里——`index/__init__.py` 会导入后者，再用 `-m` 直接跑它会打一行 RuntimeWarning）。代码里就三行：`report = Evaluator(Retriever()).run(load_cases())`，然后 `report.hit1 / hit3 / hit5 / average_time`，`report.misses` 是前 `top_k` 里没命中的那些——看失败先看这里。
- 测试（`tests/test_evaluation.py`，51 条）：名次 1 / 2 / 4 / 不在结果里 四种情况钉死 Hit@1/3/5 = 1/4、2/4、3/4；空结果、空 case 列表（指标是 0，不是除零）、反例的两种走法（查到 / 没查到）、`top_k` 生效、同一组 case 跑两遍名次一样、加载器的各种写错（未知字段 / 类型错 / 少 query / 不是 JSON / 最外层不是数组 / 文件读不到）、真项目一组（跑得通、稳、`hit5 >= 0.5` 当回归报警线、反例为空、结果都来自索引、summary 行数对得上）。自带 case 集本身也有测试：query 不重复、七类场景一个不少。
- **已知的、留给后面的**：描述类 case 现在只有两条，样本太少——**先把「同一个意思的几种说法」各补一条**，再看 embedding 到底值不值得上，比现在就动手接要稳。另外这轮真跑暴露了一个检索侧的噪声：token `exe` 会让 `vswhere.exe` 这类路径返回几百条（和 8.4 的 `py` 是同一个毛病）——那是 `retrieval.py` 评分规则的事，不归评估层管。

**假 Embedding（8.6 阶段）**

- **这一阶段只做一件事：把 hybrid 检索的管线跑通，用假的。** 8.4 说「加 embedding 就是再写一个 scorer」，8.6 验证的就是这句话——接口该长什么样、缓存放哪儿、加了之后排序会怎么变、评估比不比得出来，这些和「用的是不是真模型」无关，一个假货就能整条跑到头，还不要钱、不联网、进得了单元测试。真模型哪天接进来，换掉的只是 `Embedder` 的实现，别的都不动。
- **三个名字（`index/embedding.py`）**：`Embedder` 是接口——`dimension` 加 `embed(texts) -> 向量们`，批量进批量出、顺序一一对应（真模型一次调用能塞一串文本，逐条调是最贵的用法）。`FakeEmbedder` 是假实现：构造时给一张词表，每组词是一个「概念」，向量的第 i 维是 1 表示第 i 组词里有一个出现在文本里——全转小写、拿词做**子串**查找，没有分词器，中文只能这么撞。`EmbeddingScorer` 把它包成 retrieval 认的 `(Query, CodeChunk) -> list[Match]`：相似度是余弦，分数 = 相似度 × 权重，过阈值才给一条 `Match("embedding", ...)`——8.4 文档里留的那个 `kind` 真用上了。
- **接进检索只有一个口，`retrieval.py` 一个字没动**：`hybrid_scorers(embedder)` = 默认三个字面打分器 + 语义打分器，喂给 `Retriever(scorers=...)` 就是 hybrid；不给，结果和 8.4 逐条一致（有测试对着比）。**缓存是这一层的一部分**：Retriever 对每条 chunk 都会问一遍 scorer，不缓存的话一句查询就是 2439 次「模型调用」——查询按 `Query` 记、chunk 按 `(id, digest)` 记，文件一改 digest 就变，不会拿旧向量给新代码打分。同时替调用方挡住两种接错线：embedder 回的条数不对、维度和它自己说的对不上，都直接报错。
- **分数和阈值都按真模型的形状拍**：权重默认 40，和「整句正文」同档——语义像和正文里原样出现一样可信，但都压不过名字命中；阈值默认 0.35，低于它一条不给（没有阈值的话每个 chunk 都有一点点相似度，「查不到」这件事就不存在了）。拿去 embed 的文本是 `路径 + 符号名 + 正文`——真模型也会拿路径和符号名当上下文，早按这个形状试，省得接模型时才发现少喂了东西。`DEMO_ALIASES` 是随模块带的 11 组小抄（校验/核对/verify、改过/changed、文件/file、读回来/读、索引/index、符号/symbol、代码块/chunk、摘要/digest、刷新/重建、超时/timeout、修复/repair），手写的，照着自带 case 和这个项目的常用词挑的；表里没写的说法它一律不认识——它证明的是管线通，不是它懂语义。
- **真项目上的对照（`python -m index --hybrid`，2439 条 chunk）**：baseline 还是 8.5 那套（Hit@1 4/7、Hit@3 6/7、Hit@5 6/7，两条反例都查不到，平均 18.8 ms）；hybrid 是 **Hit@1 5/7**、Hit@3 6/7、Hit@5 6/7，平均 30.9 ms——其中第一条查询 56.7 ms（现场把 2439 条 chunk 都 embed 一遍填缓存），之后每条 ~24 ms。
- **改善的那条**：「把文件读回来」第 2 → 第 1。8.5 说它是「答案被它自己的类挡住」：那几个词在类块的正文里也原样出现，两边字面分都是 40、只能靠行号分先后；语义分进来之后，类块概念更多、被余弦稀释（0.47），方法自己 0.50——方法 60.00 反超类块的 58.86。第 3 名是另一个恰好撞上同样两组词的测试块（相似度 1.00、40 分）：假货认字不认意思，这种块它会一起捞，只是分不够高。（8.7 的粒度奖励之后，baseline 自己就能把它排到第 1——这条不再是语义分独有的功劳，重跑的数字见 8.7。）
- **诚实的结论一：8.5 留的那个靶子，假货打不中。**「校验文件有没有被改过」不限条数时命中 790 条，期望的 `SymbolIndex.read_verified` 排**第 102**（相似度 0.61）；榜首是 `agent/verify.py` 的 `Verifier.after_tool_call`（相似度 1.00）——它的注释里恰好有「改过文件就接着验一次」这套词，而 `read_verified` 用的是另一套（核对 / 对不上 / digest）。假货只会数「撞上几组词」，还偏爱撞得更纯的短块。**这不是接线错了，是假货的边界**：要分清「有没有被改过」和「改过就再验一次」，得有真模型。这条 case 继续当靶子，等真模型来打。
- **诚实的结论二：`missing_symbol_zzz` 这个反例被语义改写了。** 它含着真词 `symbol`（词表里的一组），假 embedding 认字不认「这个标识符不存在」，捞出 5 条（理由全是 embedding、关键词一条没中）——真模型多半也这样。所以**给 hybrid 准备反例得挑真正无关的词**（另一条反例「量子纠缠」仍然为空）。有测试单列一条钉住这个行为：不把它当 bug、也不悄悄放宽成「跳过」。
- **以后接真模型就三件事**：① 写一个 `Embedder` 子类，`embed(texts)` 里调 API（批量）；② 现在 chunk 是「被问到才 embed」，真模型要把「先把整个索引批量 embed 进缓存」做成显式的一步（假货算 2439 条 ~30 ms，真模型是几十秒起步，第一条查询付不起这笔钱）；③ 阈值和权重按真模型的相似度分布重新标。接完拿同一个 `Evaluator` 跑同一组 case 对比 Hit@1/3/5——8.5 立那把尺子就是为了这一刻。
- **怎么用**：`python -m index` 跑 baseline；`python -m index --hybrid` 再跑一份加假 embedding 的，两份摆在一起（同一个索引，不建两遍）。代码里就一行：`Retriever(index=..., scorers=hybrid_scorers(FakeEmbedder(DEMO_ALIASES)))`。

**排序优化：粒度与整名（8.7 阶段）**

- **问题从哪儿来**：8.5 给检索打分时抓到两条「答案被它自己的类挡住」的 case（「把文件读回来」和 `fsync`，都排第 2）。看起来像权重没调好，其实是切块粒度的一个必然结果：**类 chunk 的正文是它所有方法 chunk 正文的超集**——一个方法里的任何一句话，都必然也出现在包着它的那个类块里。同一句查询，方法命中 40 分，类块也命中 40 分（甚至更多：类块还可能顺带撞上别的词），再按「同分按行号」排，类块永远在先。8.5 当时判它「是当前打分最明显的短板」，8.7 就是来修它的。这就是 chunk 粒度影响 Retrieval 的地方：**块的边界不是检索的问题，但块的包含关系会直接变成打分的平局**，平局怎么判就成了排序的问题。
- **为什么不给「类块扣分」**：扣分是对容器块的惩罚，可类块自己也经常是正确答案（查 `ProjectIndex` 就该给类块）。真正的区别是**证据落在哪儿**：同一句话，落在几百行的类块里，多半只是因为落在它体内某个方法里；落在十几行的方法里，就是落对了地方。所以加的是「具体的块」的奖励，不是「容器的块」的惩罚——类块一分没扣，只是没拿到这一档。
- **改动一：粒度奖励（`SCORE_SPECIFIC = 10`）**。`code_matches` 里，正文命中落在 function / method 上就多给一条 `Match("specific", "更具体的 method", +10)`。两个约束把它框住：**小于「名字里的词」**（正文最多 3 个词，6×3 + 10 = 28 < 30）——正文命中再怎么攒也压不过名字命中，有测试直接拿常量钉着；**大于 0**——同分的那一对（类 40 / 方法 40）立刻分出名次。类 / 结构体拿不到它（它们是容器）。
- **改动二：整名命中单独排第一档**。查询就是某个符号的整名（`ChunkIndex.build`，或 `digest_of` 这种没有点的简单名）时，这条结果永远排最前——`_order()` 的第一项。理由不是分数不够大（100 已经不小），而是**它和别的命中不是同一种东西**：分数比的是「同类证据的多少」，整名是「你叫的名字和它一模一样」；只要允许分数相加，理论上总能堆出一个反超的数字（有测试直接拿自定义 scorer 硬塞 999 分钉这条）。档内仍然先比分数、再比位置，所以别的排序一点没变。
- **没动的**：切块一行没改（`chunks.py` / `symbols.py` 不碰），`ChunkIndex` 的数据结构、scorer 的接口（`(Query, CodeChunk) -> list[Match]`）、`scorers` 参数、embedding 那条路全都不动——粒度奖励是 `code_matches` 自己多给的一条 Match，整名档是 `_order()` 里多比的一项。
- **eval 对比（同一组 case、同一个 `Evaluator`，只换了 ranking）**：优化前（8.5/8.6 的 baseline）**Hit@1 4/7、Hit@3 6/7、Hit@5 6/7**，平均 ~19 ms，两条反例都查不到；优化后 **Hit@1 6/7**、Hit@3 6/7、Hit@5 6/7，平均 ~19 ms，反例照旧。加上假 embedding 的 hybrid 也是 6/7（8.6 里那份语义增量被 baseline 自己追平了）。
- **升上去的两条**：「把文件读回来」第 2 → 第 1（方法 50 = 正文 40 + 奖励 10，类块 40）；`fsync` 第 2 → 第 1（两个同名方法各 50，都压过自己所在的类块 40）。两条正是 8.5 诊断过的那两条。Hit@3 / Hit@5 没变（那几条本来就在前 5 里），耗时没变——粒度奖励是一次常数比较，不是新扫一遍。
- **还是查不到的那条**：「校验文件有没有被改过」一个词都不在代码里，字面层怎么调都到不了；8.6 的假 embedding 也打不中它（790 条里第 102）。这条继续当靶子——**ranking 优化解决的是「答案在你眼前却被挡住」，解决不了「答案根本不在候选里」**，后者是 embedding 的事。
- **embedding 与 ranking 的关系（后面接真模型前先想清楚）**：两者是正交的。embedding 负责**把候选捞出来、给一个语义相似度**，ranking 负责**在候选之间定先后**——8.7 改的全是后者。接真 embedding 时，语义分只是 scorer 列表里又多一条 Match（8.6 已经定好的形状），它和字面分一样被 `_order()` 排；粒度奖励对带正文命中的块照给，不会因为某条结果来自 embedding 就换一套排序规则。唯一要留意的是整名档：查询是整名时它压过一切（包括语义分）——这是有意的，「你叫得出名字」就是最强证据，测试里拿 999 分的自定义 scorer 钉着这条。
- **怎么用 / 测试**：API 一个字没变（`Retriever(...).search(...)`），变的是结果的顺序。`tests/test_retrieval.py` 新增 8 条、跟着改 4 条：方法压过包含它的类、类块没被丢掉也没拿到奖励、理由里看得到「更具体的 method」、奖励小于名字里的词（拿常量断言）、奖励不会凭空造出一条结果、硬塞 999 分也翻不过整名、普通代码关键词命中的**集合**不变（只有顺序变）、真项目上两条被挡的 case 现在第 1。`tests/test_embedding.py` 里那条「语义分把 description 提到第 1」的对照也跟着改了口径（现在 baseline 自己就是第 1）。

- **128-token 截断问题（9.5 要修的既有毛病）**：多语言模型窗口只有 128 token，9.2/9.3 量出全库近一半的块超窗被模型**悄悄截尾**——代码后半段等于没喂进去。9.5 用真实分词器复测同一份语料：**1481/2973 = 49.8%**（英文模型 49/2973 = 1.6%，它的窗口是 256）。切块本身不能动（`chunk.code` 是给 `read_file` 和字面匹配看的原文），所以修的是**喂给 embedding 的那段文本**。
- **分段方案（`index/segments.py`）**
  - **怎么切**：`compact_text()` 拼出来的文本按行贪心装进「窗口 − 2 token」的预算；第一行是位置行 `path:symbol [kind]`，**每一段都带它**（路径 / 符号名 / 类型的线索一段都不丢）；单行就超预算的按字符硬切；装得下就原样一段返回——短块切出来和 9.4 喂的**一字不差**。
  - **token 数是估计**：汉字 1 字 1 个、其余每 2 个字符算 1 个（`estimate_tokens`）。规则宁多勿少——**2793 块上实测 100% 不低于真实分词数**（换成每 3 字符只有 31.4% 覆盖）。宁可多切几段，也不能让任何一段被模型截掉。代价是段数偏多：多语言模型上 2973 块（两份语料）切成 6633 段——2149 块不止一段，约 2.2 段/块。
  - **为什么不用真 tokenizer**：缓存 key 由切分结果决定，而查缓存必须能在**不加载模型**的前提下算出 key（9.4 的热缓存「模型连加载都不加载」就是靠这条）。估计规则只依赖文本本身，冷跑热跑算出来一模一样。
  - **一个块多个向量，打分取最大**：`EmbeddingScorer` 对每段算余弦，chunk 的语义分是**段间最大值**（max-pooling，不取平均——平均会把「有一段很像」稀释成「整体一般像」，掉到阈值以下）。一个块的最终分数还是 `Retriever` 那套「各 scorer 分数相加」，**排序规则一个字没动**。
  - **缓存 key / 命名空间带版本**：chunk 向量 key 变成 `id|digest#s0`、`#s1`…（一段一条）；命名空间从 `…#compact-v1` 变成 `…#compact-v1+segment-v1`——**切法一改自动作废旧向量**，分段和不分段的两套向量在同一缓存目录下也不会串（这正是 9.4 / 9.5 对照的机制）。`--no-segment` 关掉分段复现 9.4。
  - **诊断行**：每组报告后多一行 `[segment] 分段后仍有 x/y 条超过模型窗口（%，窗口 N token）`——拿**真实分词器**数的，回答「估计切法到底修好了没有」；`--no-segment` 时量的是整块，两个数摆一起就是前后对照。

  分段把目标块最像的那一段从 0.2339 抬到 0.3034（+29.7%）——**截断确实修好了，但没修到阈值以上**（低于 0.35 的块根本进不了候选，「名次」无从谈起）。同一块用英文问（`how do we know a file changed on disk`）在 9.4 / 9.5 下都稳定排在 848 / 849（共 1219 条），一条的差别是噪声。结论：瓶颈已经从「喂进去的文本被截掉」换成「这个模型对这条中文查询的判别力」——**再往下要么换更大窗口 / 更强的模型，要么动阈值和权重（本阶段明令不许），要么改切块文本的设计**。另一条 `read_verified` case（「把文件读回来」）两组都是第 1。
- **反例量出来的两件事（都写进了 case 文件的注释）**
  - **英语整句在这份语料上做不了反例**。测试方法名本身就是英文整句（`test_missing_library_says_how_to_install`），`how` / `to` / `in` / `the` / `from` / `over` 全在里面，字面打分的「名字里的词」必然命中。第一版反例里的 `SELECT * FROM users WHERE id = 1`（撞 `where` / `from`）和 `kubectl delete pod`（`delete` 是 `deleted` 的子串）实测都是假阳性，换成了中文整句和标识符样的词。**结论：这份语料的负例只有两种形状站得住——中文整句（拆词后是一个词，代码里出现不了）和 snake_case 标识符（同样是一个整词）。**
  - **真模型会假阳性**：多语言组 3/6（`missing_symbol_zzz`、`kubernetes_ingress_controller`、`ffmpeg 转码`），英文模型组把 `量子纠缠` 捞出 1 条（它对中文的相似度本来就是噪声带，9.2 已量过）。这些全部来自 embedding 那一条理由，字面 scorer 一条都没中——**语义检索确实改写了「查不到」的定义**，读反例数字时得把这条记在账上。
- **耗时与调用次数（多语言组；整轮 = 四组全跑）**

  | 场景 | 9.4 不分段 | 9.5 分段 |
  | --- | --- | --- |
  | 首轮（`--no-cache`，全量嵌入）批量预热 | 48.1 s | 75.6 s |

**Embedding 接入 SearchChunksTool / Agent（9.4 阶段）**

- **一句话**：9.0~9.3 建的 embedding 线（provider / 紧凑文本 / 批量 / 缓存）一直只在 `index/` 的评估入口里跑，8.8 接进 Agent 的 `search_code_chunks` 从来只用字面分数。这一阶段把两者接上：工具多一个 `embedding` 参数，默认 `off`，开了才有第四条语义 scorer。
- **配置方式**
  - 环境变量 `SEARCH_CHUNKS_EMBEDDING`（写 `.env` 或直接设系统环境变量都行），`main.py` 装配工具时读；值不合法**启动即报 `ConfigError`**（列出可选项），不会等第一次检索才发现拼错。
  - 只认四个名字：`off` 不在 `index.providers.PROVIDERS` 里——它的意思是「这条线根本不接」，不是某个 provider；其余三个就是 provider 名字，有测试钉着 `SEARCH_EMBEDDING_MODES` 和 `PROVIDERS` 名单一致。

    | 模式 | 什么意思 | 需要什么 |
    | --- | --- | --- |
    | `off`（默认） | 纯字面检索，8.8 起的老行为 | 什么都不用 |
    | `fake` | 演示用假 embedding（词表小抄，离线） | 什么都不用 |
    | `local` | 本地英文模型 `all-MiniLM-L6-v2` | `pip install sentence-transformers`，首次联网下模型 |
    | `multilingual` | 本地多语言模型 `paraphrase-multilingual-MiniLM-L12-v2`（中文查询用这个） | 同上 |
- **懒加载（模型到第一次真检索才加载）**
  - 构造工具、注册进 `ToolRegistry`、`Agent` 启动——全程只读一个字符串，不 import 模型、不联网；`SearchChunksTool.__init__` 只造一个 `LocalEmbedder` 壳子（9.0 起构造就不加载）。
  - 第一次 `execute()` 走 `_prepare_embedding()`：先建索引（批量预热的来源是 chunks，空索引等于什么都没预热），再 `scorer.prefetch()` 一次批量算齐全部 chunk 向量——**模型就是在这一步加载的**。
  - 附带的好处（实测）：缓存全命中时这一步几乎是空的——新进程第一次查询 643 ms、`embed()` 调用 0 次，模型连加载都没加载。
- **降级策略（语义检索坏了不许拖垮工具）**，三层：
  1. `DegradingScorer`（`index/embedding.py` 新增）：把语义 scorer 包一层，**调一次炸了就永久关掉自己**（`error` 记第一个错因、之后不再问里面），返回空匹配——`Retriever.search()` 完全不知道出过事，照常拿字面 scorer 出结果。
  2. `_prepare_embedding()` 里 `prefetch()` 的 try/except：模型没装 / 下不动 / 加载失败 → 关掉语义分，**检索退回字面**。
  3. `VectorCache` 自己的降级（9.3 就有）：缓存文件坏了 / 写不进去 → 当没有缓存，重算一遍。
  - 唯一不降级的是**建索引失败**——那是 baseline 也会遇到的整体失败（字面检索同样建不动），不该假装降级成功。
  - 错因留在 `SearchChunksTool.embedding_error`（没降级是 `None`），工具照常返回结果。
- **Agent RAG 流程没变**：工具还是只给位置（`相对路径:起止行号` 符号 [类型] 分数 命中原因），语义命中的原因写「语义相近 0.xx（+分数）」，模型拿行号去 `read_file` 读磁盘上的当前代码。**返回内容格式、`top_k` 语义、`max_top_k` 一个字节没改**；`retrieval.py` 的权重表也没动——没有为了提高命中率调任何参数。
- **真实验证（真 LLM + 多语言模型，2780 块语料）**：两条查询的工具序列都是 `search_code_chunks → read_file`，`embedding_error` 全程 `None`：
  - **英文**：`Where is the scoring loop that turns the scorers' matches into ranked results?` → `search_code_chunks("scoring loop rank results scorers matches")`（34.6 s，这一次把模型加载 + 全量预热付掉了）→ `search_code_chunks("score")`（0.9 s）→ `read_file index/evaluation.py` → `read_file index/retrieval.py`。答案定位 `index/retrieval.py:247-266`（打分循环），**并且识别出第一次检索的头名 `index/evaluation.py:_rank` 不是它要找的**——读原文核对后主动排除。
  - **中文**：`检索分数是在哪里算出来的？` → `search_code_chunks` ×2（1.0 / 0.96 s）→ `read_file tests/test_retrieval.py` → `read_file index/retrieval.py`，答出 `index/retrieval.py:258`（`score=sum(item.score for item in matches)`），行号回查正确。
  - 诚实记一笔：语义分**不保证**目标排第一（英文那条头名是别的块，靠模型自己读原文核对才否掉）。工具给的是候选和理由，最终判断在模型——这正是 8.8「只给位置」的设计。
- **耗时（同一台机器，2780 块）**：

  | 场景 | 耗时 |
  | --- | --- |
  | embedding 首次加载（import torch + 载权重 + 1 条编码） | 38.8 s |
  | 冷缓存首次查询（建索引 + 加载模型 + 全量预热 2780 条 + 检索 + 落缓存） | 57.9 s |
  | 同进程重复查询 | 270 ms |
  | 新进程 + 热缓存，首次查询（模型不加载） | 643 ms |
  | 新进程 + 热缓存，重复查询 | 195 ms |

  热缓存那两行是关键：向量全从 9.3 的 JSON 缓存里读，`embed()` 调用 0 次、模型根本没加载——**缓存的收益在 Agent 场景里比评估里更明显**（Agent 一次会话里会反复调这个工具）。
- **兼容性（一个字节没改的）**：`retrieval.py`（连 `DEFAULT_SCORERS` 的权重都没动）、`Retriever` / `CodeChunk` / `SymbolIndex` / `Embedder` 接口、RepairLoop / Verifier、chunk 边界、`search_code_chunks` 的返回内容与格式。动过的只有装配处：`tools/search_chunks.py`（加参数、懒加载、降级）、`index/embedding.py`（新增 `DegradingScorer` 与 `cache_for`）、`index/__main__.py`（改用 `cache_for`，行为不变）、`config.py`（读环境变量）、`main.py`（装配 + 横幅）、`.env.example`。
- **新增 35 条离线测试（`tests/test_search_chunks_embedding.py`）**：**off 模式**——默认不接、结果和裸 `Retriever` 逐条相同、不碰缓存目录、off + 注入 embedder 直接报错；**模式**——坏名字报错并列出可选项、大小写 / 空格不敏感、fake 装配形状（守卫在、顺序对）、`cache=False`、注入的 embedder 原样使用、每个 provider 名字都能开；**懒加载**——构造 0 次加载、第一次查询 1 次、第二次仍 1 次、首批就是全部 chunk、第二次只嵌查询；**语义生效**——字面全不中的查询能捞出目标块、输出还是五段格式；**降级**——加载失败 / 搜索中途炸 / 缓存文件损坏三种都退回字面且不再惊动模型、`DegradingScorer` 单元行为、第一个错因不被覆盖；**缓存复用**——第二个工具零嵌入、改一个文件只重嵌它的块、缓存文件名带正确的命名空间；**配置**——默认 / 空值 / 规范化 / 坏值、名单与 `PROVIDERS` 一致；**装配**——`main.build_registry` 默认 off、跟环境变量走、坏值启动报错。全部离线：假模型只有 `encode` + `get_sentence_embedding_dimension` 两个方法，缓存落临时目录，真模型不进测试。

**Embedding 优化：紧凑文本 / 批量 / 缓存（9.3 阶段）**

- **三个问题，三个答案**。9.2 把病因量清楚了：① 全库 45.7% 的块超过多语言模型的 128 token 窗口，整块代码喂进去被截尾；② `EmbeddingScorer` 对 chunk 逐条 embed，2616 个块就是 2616 次单条模型调用；③ 没有 cache，每开一个新进程都要重算全库。9.3 分别用 `compact_text`（喂什么）、`prefetch`（怎么算）、`VectorCache`（怎么不重算）回答。**验收标准是「结果不变」**：四组 Hit@1/3/5 一个数字没动，变的是耗时和调用次数。
- **紧凑文本（`index/compact.py`）**
  - **为什么不直接改 chunk 的 code**：chunk 正文是给 `read_file` 和字面匹配看的原文（8.3 定的），给它瘦身会连带改掉 `SearchChunksTool` 的返回和字面命中——所以只为 embedding **另拼一段字符串**，`CodeChunk` 一个字段没动，`SearchChunksTool` 的返回内容一个字节没变。
  - **拼什么**：三段——**位置行** `path:symbol [kind]`（文件名 / 符号名 / 类型在一行里，字面线索一个不少）；**描述段**（Python 的 docstring，空白压平、截到 `MAX_DOC_CHARS = 200` 字符，常是整块里最像人话的部分）；**代码开头**（截到 `MAX_CODE_CHARS = 400` 字符，没有 docstring 的 C/C++ 块就靠它）。上限都在常量里，换策略只动这一个文件。
  - **掏空那一下是实测逼出来的**：docstring 本来就长在代码开头里，描述段再抄一遍 = 同一段文字喂两遍——实测多语言模型上超窗比例反而从 46.2% 涨到 51.2%，评估里多语言组 Hit@1 掉到 5/7（`fsync` 被一个测试块用 +14.2 的语义分挤到第 2）；把 docstring 从代码开头的原位掏空之后，两边各出现一次，回到 6/7。
  - **数字（当前语料 2709 块，tokenizer 实测）**：

    | 模型（窗口） | 老文本超窗 | 老文本平均 | 紧凑文本超窗 | 紧凑文本平均 |
    | --- | --- | --- | --- | --- |
    | L6（256 token） | 462/2709（17.1%） | 207 token | **41/2709（1.5%）** | 128 token |
    | L12（128 token） | 1253/2709（46.3%） | 205 token | 1331/2709（49.1%） | **128 token** |

    L12 的超窗条数没降反微升：短块补上了位置行，而 128 token 的窗口本来就装不下大多数块——**这是模型选型问题（9.2 已记），不是拼法问题**；拼法能保证的是「截掉之后剩下的全是有效信号」（平均 205 → 128）。（9.2 README 里的 17.0% / 45.7% 是在 2616 块的旧语料上量的，同一回事。）
  - **确定性**：纯字符串拼装，不取时间、不取 id、不取随机数——缓存 key 依赖它稳定，有测试钉着「同输入同输出」。
  - **改了拼法怎么办**：`TEXT_STRATEGY = "compact-v1"`，评估入口把它拼进缓存命名空间——拼法一改（版本 +1），旧向量自动作废，不会拿旧拼法算出来的向量冒充新结果。
- **批量（`EmbeddingScorer.prefetch`）**
  - **为什么批量能省调用**：`Embedder.embed(texts)` 从 9.0 起就是批量接口，但老路是 scorer 每条 chunk 各调一次单条——「批量」这个词根本没有落到模型上。现在打分前一次把全部 chunk 文本攒齐，走「内存 → 磁盘缓存 → 模型」，**模型那一步只调一次**。实测：2709 个 chunk + 9 条查询 = **2718 条文本、10 次 `embed()` 调用**（1 次全量预热 + 9 条查询各一次），原来是 ~2718 次。
  - **顺序对应**：预热的输入顺序就是 chunks 的顺序，向量按序回填各自的 key，测试拿 `RecordingEmbedder` 记下每一批的内容和顺序钉着；查询向量仍是一条一条算（查询本来就是一次一条）。
  - **接口没动**：`Embedder` 还是 `dimension` + `embed(texts)`；`hybrid_scorers()` 的旧调用形状照常可用（只多了 `cache=` / `chunks=` 两个可选参数）。
  - **预热从查询里拆出来**：`python -m index` 里先 `scorer.prefetch()` 再跑评估——一次预热的耗时单列（`[embedding] ... 批量预热 X.X s`），不混进单条检索的平均耗时，模型跑不动也在这里尽早报。
- **缓存（`index/vector_cache.py`）**
  - **key 与失效规则**：chunk 向量 key = `chunk.id|chunk.digest`（**文件一改，digest 变，旧条目自动找不到**）；查询 key = `query:文本`（同样的查询第二次直接命中）。文件名 / 命名空间 = `类名:模型名#compact-v1`（FakeEmbedder 用词表指纹）——**换模型 = 另一个命名空间 = 另一个文件**，旧文件连读都不读；拼法版本同理由。格式版本 `CACHE_VERSION` 变了，旧文件自动当空。
  - **查询向量也进缓存，但不会串模型**：查询 key 里只有文本，靠的是**命名空间**隔离——英文模型和多语言模型的查询向量落在不同文件，物理上不可能串用。
  - **读写失败只降级**：文件损坏 / 只读 / 磁盘满 → 记在 `degraded` / `load_error` / `write_error` 上，坏条目跳过、**不往外抛**；baseline 和关键字检索完全不受影响。测试把「缓存坏了」和「完全没有缓存」两条路都跑了一遍。
  - **精度与体积**：向量按 6 位小数落盘（`PRECISION`）——**冷跑和热跑的评估结果逐字相同**，证明这个舍入不影响排序；文件因此小一截（实测 L6 11.07 MB、L12 11.10 MB、假货 403 KB）。
  - **不污染项目**：默认目录 `~/.cache/universal-code-agent` 在用户目录下，不在项目里、不会被 `ProjectIndex` 扫到；**不提交任何模型文件或向量数据**。`--no-cache` 关缓存（对照实验用）。
- **四组数字（真实评估，`python -m index --multilingual`，同一台机器）**：

  | 组 | Hit@1 | Hit@3 | Hit@5 | 平均耗时（首轮 / 重复） | 反例 |
  | --- | --- | --- | --- | --- | --- |
  | 字面 baseline | 6/7 | 6/7 | 6/7 | 23.1 / 21.1 ms | 2/2 都没查到 |
  | 假 embedding hybrid | 6/7 | 6/7 | 6/7 | 32.5 / 29.9 ms | 1/2（同 9.2） |
  | 英文模型 hybrid（L6） | 6/7 | 6/7 | 6/7 | 205.8 / 150.5 ms | 1/2（同上） |
  | 多语言模型 hybrid（L12） | 6/7 | 6/7 | 6/7 | 215.0 / 188.5 ms | 1/2（同上） |

  首轮（空缓存）整进程 **100 s**：批量预热 L6 48.9 s、L12 43.8 s、假货 0.0 s，都单列在 `[embedding] embed() 调用 N 次；嵌入 M 条文本；缓存命中 K 条；批量预热 X.X s` 这一行里；重复一轮（缓存全命中）整进程 **4 s**，2718 条全部命中、`embed()` 调用 **0 次**（模型连加载都没加载），Hit@1/3/5 与首轮逐字相同。
- **9.2 → 9.3 的耗时对比（同样的组、同样的 case）**：L6 每条查询 6593.8 → **205.8**（首轮均摊）/ **150.5 ms**（重复），L12 11702.1 → **215.0 / 188.5 ms**。9.2 的数字里每条查询都要把全库块逐条 embed 一遍（2616 次单条调用 × 9 条查询）；9.3 只付一次批量预热，之后每条查询是「读缓存 + 2709 次余弦」——残余的 150~215 ms 是逐 chunk 打分本身的开销（`Retriever` 对每个块跑一遍 scorer 列表，`retrieval.py` 这一阶段不许动），不再是模型调用。
- **诚实的结论**：① 靶子「校验文件有没有被改过」**还是没打中**——紧凑文本下 `SymbolIndex.read_verified` 的相似度 **0.2339**，仍低于 0.35 阈值（9.2 是 0.2273，几乎没动：截断少了，但这条查询与这段话的语义距离是模型给的）；② 命中率四组全平（6/7），这一阶段**没有为了 Hit@k 动权重 / 阈值 / 排序**——只改了输入文本、调用方式和缓存；③ 剩下的瓶颈是模型的 128 token 窗口和 chunk 粒度，留给下一阶段。
- **兼容性（一个字节没改的）**：`retrieval.py`、`CodeChunk` / `SymbolIndex` 的数据结构、Agent / RepairLoop / Verifier / Tool、`Embedder` 接口、`FakeEmbedder`、`LocalEmbedder`、`SearchChunksTool` 的返回内容；**没有 embedding 时 baseline 结果不变**（有测试直接拿 `DEFAULT_SCORERS` 跑同一组 case 比对）。
- **新增 45 条离线测试（`tests/test_embedding_optimization.py`）**：**紧凑文本**——三段都在、docstring 只出现一次、同输入同输出、非 Python 块可用、上限生效；**批量**——一批只调一次 `embed()`、输出与输入顺序对应、计数正确；**缓存单元**——key 形状、digest 变化失效、命名空间不同不串用、坏文件降级、外来命名空间拒读拒写、精度舍入；**缓存集成**——命中 / 未命中、模型换了失效、缓存坏了照常检索、重复运行零嵌入；**兼容**——baseline 不受影响、`hybrid_scorers` 老形状可用、评估入口四组齐全。全离线：假模型只有 `encode` + `get_sentence_embedding_dimension` 两个方法，真模型不进测试、不下载、不提交。

**多语言 Embedding 验证（9.2 阶段）**

- **为什么需要多语言模型**：9.1 的诊断结论是「机制是活的，缺的是模型的语言能力」。`all-MiniLM-L6-v2` 是英文单语模型——中文查询下全库相似度挤在 0.35–0.41 一条噪声带里，没有区分度，排序等于随机。而这个项目的注释 / docstring 几乎全是中文，查询也常是中文：需要一个中英文都能分辨的模型。
- **加了什么：只有配置，没有机制。** `index/providers.py` 注册第三个 provider `"multilingual"`：默认 `paraphrase-multilingual-MiniLM-L12-v2`，传 `model_name=` 就覆盖——**模型名是配置，不是业务逻辑**。`index/__main__.py` 的评估入口只给 provider 名字（`create_embedder("multilingual")`），也顺手把英文那组从 `LocalEmbedder()` 改成 `create_embedder("local")`：入口里从此没有模型名。9.0 说「加 provider = 写个子类 + 注册表加一行」，这次连子类都不用写（复用 `LocalEmbedder`）——一行注册 + 一行默认值常量，完事。
- **评估方式**：`python -m index --multilingual`。四组共用同一个 `ChunkIndex`、同一组 `evaluation_cases.json`、同一个 `Evaluator`，唯一变量是 scorer 列表里那个 embedder。`--local` 仍是三组，不给参数仍是纯 baseline——向后兼容。多语言模型跑不动（没装库 / 模型名打错 / 下载失败）时，前三组的报告照常保留，退出码 1，报错沿用 `EmbeddingUnavailable`。
- **四组数字（同一台机器，整个项目的索引）**：

  | 组 | Hit@1 | Hit@3 | Hit@5 | 平均耗时 | 反例（2 条本来就该查不到） |
  | --- | --- | --- | --- | --- | --- |
  | 字面 baseline | 6/7 | 6/7 | 6/7 | 20.0 ms | 2/2 都没查到 |
  | 假 embedding hybrid | 6/7 | 6/7 | 6/7 | 33.3 ms | 1/2（`missing_symbol_zzz` 被捞出 5 条） |
  | 英文模型 hybrid（L6） | 6/7 | 6/7 | 6/7 | 6593.8 ms | 1/2（同上） |
  | 多语言模型 hybrid（L12） | 6/7 | 6/7 | 6/7 | 11702.1 ms | 1/2（同上） |

- **与英文模型的区别（实测，同一条中文查询）**：**区分度**——英文模型全库相似度 0.35–0.41（噪声带，第一名是 `_newline`）；多语言模型最高 0.5887、均值 0.2954、最低 -0.0196，分布真的拉开了，而且前 8 名全是验证 / 检查语义相关的块（`test_verify` 的三条、`agent/repair.py` 的指纹函数、`test_compile` 的诊断测试类）。**中文语义排序从「随机」变成了「有意义」**。**上下文长度**——`all-MiniLM-L6-v2` 是 256 token（全库 17.0% 的块超限），`paraphrase-multilingual-MiniLM-L12-v2` 只有 **128** token（**45.7%** 超限）：层数多了、窗口反而小了一半，整块代码喂进去近一半被切尾巴。**速度**——全项目 2616 块，L6 逐条嵌入约 58 s、L12 约 105 s（CPU；scorer 的块向量是一条一条 embed 的，见下）。
- **靶子还是没打中，但这次知道为什么了**：「校验文件有没有被改过」在多语言组前 5 无命中，第一名是 `tests/test_compile.py:CompileToolDiagnosticsTest`（0.5887）。探针（跑完即删）把 `read_verified` 的处境钉死了：① 它的整块文本（路径 + 符号名 + 正文）**368 token**，是模型上限 128 的 3 倍——尾巴根本没进模型；② 能进模型的部分也被路径 / 符号名 / 英文签名稀释：同一查询，**整块 sim 0.2273，只留中文 docstring sim 0.3265**（+0.10）；③ 同一句译成英文查询，`read_verified` 排 **259/2616**（sim 0.3313，前 10%），中文原文只排 2092/2616——**连多语言模型，这句中文也比它的英文译文难**；④ 就算不截断不稀释，0.3265 离前 5 的门槛（约 0.54）仍有距离——**这不再是模型语言能力的问题，是「喂给模型的文本」和「块的粒度」的问题**。
- **后续怎么选模型（这一阶段量出来的依据）**：① **中文项目优先多语言模型**——区分度是数量级的差别；英文模型在中文上排序等于随机。② **看 `max_seq_length`，不只看层数和维度**——L12 是 128、L6 是 256，45.7% 的块超限意味着近一半文本只嵌了个开头；下一个模型（`bge-m3`、`multilingual-e5` 这类 512 token 的）语言覆盖和窗口大小一样重要。③ **换模型永远是改一个名字**：`create_embedder("multilingual", model_name="BAAI/bge-m3")`，或往 `PROVIDERS` 加一行——Retriever / 评估 / Agent 全不动。④ 下一批要解决的两件事：**首轮成本**（2616 个块是**一条一条** embed 的——`EmbeddingScorer` 每次只喂一条文本，批量接口在 9.0 就有了但这条路没用上；cache 从 9.0 起也一直挂着）和**块文本瘦身**（现在整段代码都喂，45.7% 超限）。
- **新增 17 条离线测试（`tests/test_multilingual_embedding.py`）**：**模型配置**——`"multilingual"` 注册在案、默认模型对、`model_name=` 可覆盖、不认识的名字报错列出三个；**参数传递**——模型名到 loader、`batch_size` 和文本顺序到模型、维度来自模型；**不可用模型**——下载失败 / 模型名不存在都包成 `EmbeddingUnavailable` 且带原因；**评估入口**——`--multilingual` 出四组（标题逐个对）、注入口原样生效、四份报告、多语言组挂掉时前三个报告保留且退出码 1；**原有分组不动**——`--local` 仍三组、不给参数仍只有 baseline、baseline 的 `Hit@1 2/2` 数字一个没变。全离线：假模型只有 `encode` + `get_sentence_embedding_dimension` 两个方法，不装库、不联网、不下载模型、不提交模型文件。

**真实 Local Embedding 评估（9.1 阶段）**

- **目标：不问「接口通不通」（9.0 已证），只问「真模型接上以后，检索到底强了多少」。** 要求里钉着不许动的三样——Retriever 排序逻辑、Embedder 接口、Agent / Tool / RepairLoop——这一阶段一个字节没碰；动过的只有 `index/__main__.py`（评估入口）和新增的测试。sentence-transformers 是可选的实验依赖，没进 requirements.txt，没装的机器照样跑全部测试。
- **入口：`python -m index [--hybrid|--local]`，组是递进的。** 不给参数只跑 8.5 那套字面 baseline；`--hybrid` 加一组挂 `FakeEmbedder` 的；`--local` 再加一组挂真 `LocalEmbedder`（默认 `all-MiniLM-L6-v2`）。三组共用一份索引、同一组 case（`evaluation_cases.json` 一个字没改）、同一个 `Evaluator`——**唯一的变量就是 scorer 列表里多没多 embedding**。本地模型跑不动（没装库 / 下不下来）时，前面几组的报告照常留在屏幕上，末尾一句 `[本地模型不可用] …` 说明情况，退出码非 0——不白跑。`--local` 是真实实验：测试永远注入假 embedder，真模型不进测试。
- **三组数字（同一台机器，整个项目的索引）**：

  | 组 | Hit@1 | Hit@3 | Hit@5 | 平均耗时 | 反例（2 条本来就该查不到） |
  | --- | --- | --- | --- | --- | --- |
  | 字面 baseline | 6/7 | 6/7 | 6/7 | 19.9 ms | 2/2 都没查到 |
  | 假 embedding hybrid | 6/7 | 6/7 | 6/7 | 32.6 ms | 1/2（`missing_symbol_zzz` 被捞出 5 条，8.6 起就有） |
  | 真模型 local hybrid | 6/7 | 6/7 | 6/7 | 9129.1 ms | 1/2（同上） |

- **命中率为什么三组一样**：7 条该找到的 case 里，6 条是字面就能打中的（文件名 / 符号名 / 关键词 / 英文词），8.7 的粒度奖励和整名档已经把它们都排在第 1；唯一剩下的是那条中文人话靶子——而它恰好是 embedding 该管的事，它没被找到，三组就都是 6/7。**这一阶段量的不是「embedding 有没有用」，而是「这个模型有没有用」。**
- **靶子的诊断（临时探针，跑完即删）**：查询「校验文件有没有被改过」在真模型下前 5 一条都没命中，第一名是 `tools/edit_file.py:_newline`。把前 8 名拉出来看：**全部是纯语义分，相似度全挤在 0.35–0.41**——紧贴阈值的一个「近随机」分布，说明模型对这条中文查询没有区分能力。对照组：把同一句译成英文（`check whether the file was modified`）再查，语义分立刻有用武之地——`tests/test_edit_file.py:ResultTest.test_the_file_on_disk_really_changed`（名字里就有 file / changed）拿到语义 0.38（+15.08 分），总分 109.08 排第 1。**同一条管线、同一个模型，英文查询能靠语义加分，中文查询只剩噪声**：`all-MiniLM-L6-v2` 是英文单语模型，而项目里的注释和 docstring 几乎全是中文。期望目标 `SymbolIndex.read_verified` 在两次查询里都没进前 8——不是被排序挡了，是根本捞不出来。
- **把问题钉准，而不是放弃**：8.5 起这条靶子的判词是「留给真 embedding」；9.1 量完，判词改成「留给**对的** embedding」——语义机制本身是好的（挂着假货 / 真模型的两组都能凭语义捞出东西，连反例 `missing_symbol_zzz` 都被捞了出来，那是 8.6 就记在案的副作用），唯独中文语义打不动单语英文模型。**9.0 的 provider 抽象就是为这个留的**：换 `paraphrase-multilingual-MiniLM-L12-v2` 这类多语言模型只改一个模型名（`LocalEmbedder("…")` 或 `create_embedder("local", model_name="…")`），Retriever、评估、Agent 全都不用动——这是下一阶段的自然起点。
- **耗时怎么读**：baseline 19.9 ms、假货 32.6 ms 是每条查询的平均；真模型 9129.1 ms 是被第一条拉高的——第一条要把全项目的块现场 embed 一遍填 `EmbeddingScorer` 的缓存（同进程内之后只嵌查询），而**不做 embedding cache 是本阶段明令的限制**（9.0 里也写着「下一阶段处理」）。所以这个数字是「每开一个新进程评估一轮」的真实成本，不是每次查询的成本；真接进 Agent（8.8 的 `search_code_chunks`）时，第一次调用同样要付这笔钱。
- **新增 7 条离线测试（`tests/test_evaluation_entry.py`）**：**选组**——不给参数只跑 baseline 且 scorers 就是 `DEFAULT_SCORERS`、`--hybrid` 第二组挂的是 `DEMO_ALIASES` 的假货、`--local` 三组且第三组的 `LocalEmbedder` 构造完没加载（没装库的机器上这一步也不许报错）、注入口塞进去的 embedder 原样被用；**报告**——每组各一份摘要（`Hit@1` 和耗时各出现一次）、`--local` 出三份、本地模型不可用时退出码 1 且前两组的报告完整保留。全部走注入口和假 embedder，不联网、不装库、不下载模型。
- **顺带记一笔**：sentence-transformers 6.x 里 `get_sentence_embedding_dimension()` 已改名 `get_embedding_dimension()`（旧名还能用，会打一行 FutureWarning）。9.0 定的「对模型只要求那两个方法」没变，要不要跟进改名是个一行的小决定，留到下次动 `local_embedding.py` 时一起做，这一阶段不碰。

**可插拔的本地 Embedding Provider（9.0 阶段）**

- **这一阶段做「换模型」的第一步：把 embedding 实现变成可插拔的一层，并接上第一个真模型实现。** 8.6 定好的 `Embedder` 接口（`dimension` + `embed(texts)`）一个字没改——Retriever / EmbeddingScorer / 评估都不认识模型，只认识接口；`FakeEmbedder` 原样保留，离线测试和演示继续用它。
- **`LocalEmbedder`（`index/local_embedding.py`）**：包一个本地 sentence-transformers 模型。对模型的要求只有两个方法——`encode(texts, batch_size=...)` 和 `get_sentence_embedding_dimension()`，正是 sentence-transformers 的形状；**模型细节不出这个文件**，Retriever 那边什么都看不到。批量进批量出、顺序一一对应；条数对不上（模型回了几条和给的不一样）当场报错——不报的话向量和代码块会静默错位。
- **加载是懒的，失败是可行动的**：构造 `LocalEmbedder`（或 `create_embedder("local")`）不碰模型、不联网——没装库的机器上照样拿得到对象；第一次 `embed()`（或问 `dimension`）才加载，加载失败一律包成 `EmbeddingUnavailable`：没装库的提示 `pip install sentence-transformers`，装了拉不动的说明第一次用要从 HuggingFace 下载、得联网。失败不粘住——这一次断了，下一次还会再试。空批次 `embed(())` 直接回空，不为零条文本去拉起模型。
- **sentence-transformers 是可选依赖**（它拖着 torch，不小），**没进 requirements.txt**：要用的时候再 `pip install sentence-transformers`——没装的机器上测试、Agent、检索全部照跑。
- **工厂（`index/providers.py`）**：`create_embedder(provider, **kwargs)` 按名字拿 Embedder——`"fake"`（默认，8.6 的演示小抄）和 `"local"`；名字拼错直接报错并列出可选项。**将来接 API provider 就两件事**：写一个 `Embedder` 子类，往 `PROVIDERS` 注册表加一行「名字 → 构造函数」，别处不动。「可插拔」指的就是这个：换 provider 不改 Retriever、不改评估、不改 Agent。
- **没动的**：`Retriever` / 排序逻辑（`retrieval.py`）、`EmbeddingScorer` / `hybrid_scorers` / `FakeEmbedder`（`embedding.py` 一个字节没改）、Evaluation、Agent / RepairLoop / Verifier / 工具链路。新增的只有 `index/local_embedding.py`、`index/providers.py` 和 `index/__init__.py` 的导出。不引入向量数据库（FAISS / Milvus / Chroma），不做 embedding cache——那是下一阶段。
- **新增 22 条离线测试（`tests/test_embedding_providers.py`）**，不装库、不联网、不下载模型：**工厂**（默认 fake、自定义词表、local 构造不加载、参数透传、名字不认识列出可选项）；**LocalEmbedder 对模型的封装**——一个假模型（就那两个方法）全测：批量进批量出且顺序对应、向量是纯 float 元组、一批只调模型一次、维度来自模型、自定义 batch_size / model_name 传到、模型只加载一次、空输入不惊动模型、条数对不上当场报错、batch_size 0 拒绝；**加载失败**——缺库走 `sys.modules` 置空触发真 ImportError 那条路、loader 炸了包成 `EmbeddingUnavailable` 且带原因、自定义 loader 自己抛的 `EmbeddingUnavailable` 原样冒出、失败后下一次还会重试；**接回管线**——挂着假模型的 LocalEmbedder 塞进 `hybrid_scorers`，在真 `Retriever` 上查询命中、理由里看得到「语义相近」，证明 Retriever 一行没为它改。

**验证 RAG 在 Agent 里的真实使用（8.9 阶段）**

- **这一阶段不加功能，只回答一个问题：8.8 接进来的 RAG，Agent 在真活儿里用不用、什么时候用。** 方法：真项目上跑只读的分析任务、临时小工程和项目副本上跑修改任务，逐条查 trace——调没调 `search_code_chunks`、有没有接着 `read_file` 读正文、有没有进 `edit_file → 自动验证` 的流程。找到问题的话只允许一种修法：最小改提示词（工具设计不许动）；`index/`、`Retriever`、Embedding、已有工具一个字节没改。探针是一个临时脚本，跑完即删，不进仓库。
- **分析任务（真项目，3 个）：RAG 是自发首选。** 三个问题都是「知道有这么个东西、不知道在哪儿」——「tool-calling 循环在哪个文件的哪个函数」「+10 的粒度奖励在哪儿定义和使用」「怎么判断已索引的文件被改过」。三次的第一枪全是 `search_code_chunks`，拿到位置再 `read_file` 精读，答案里的引用逐条回查正确。第三个是语义型（「怎么判断被改过」一个词都不在代码里，8.5 起就记在案的那条靶子），RAG 没直接把它带到面前，模型自己退到 `search_code` 找线索、再读文件补齐——提示词里「先用它缩小范围、再 `read_file` 精读」的预期用法就是这个意思，检索榜单打不中不等于任务卡死。
- **修改任务（3 个）：目标叫得出名字时，模型自己选了关键词搜索。** 三条任务分别是「`percent_error` 期望值为 0 时除零」「给 `clamp_value` 补一个 main」「把 `htmlcov` 加进跳过名单」——目标都是字面量名词。模型的第一枪全是 `search_code`（基本一击命中），然后 `read_file` → `edit_file` → 自动验证。**这不是 RAG 失灵，是分工用对了**：8.8 的 description 里写明了「关键词找单行用 `search_code`、找整块 / 按语义挑用 `search_code_chunks`」，模型按分工挑工具，正是想要的行为。所以提示词没有改——本阶段只允许在「发现 Agent 不主动使用 RAG」时动它，这次没触发。
- **副本任务跑出了完整链路，自动验证在真项目上也真的在拦人。** 项目副本上「把 `htmlcov` 加进跳过名单并补测试」：`read_file tools/tree.py → read_file tests/test_list_files.py → edit_file（加进 IGNORE_DIRS）→ 自动 run_tests（全绿）→ edit_file（补测试）→ 自动 run_tests（全绿）`，报告「第 1 轮就通过；第 2 轮就通过；最终成功」，最终回答里的引用逐条正确。小工程那两条同样走完——Python 那条改完自动跑测试；C++ 那条第一次编辑不完整，**自动编译拿 VS 的 `cl.exe` 当场报出 LNK1561（没有入口点）把模型拉回去补完**，最后模型还自己跑了编出来的 exe 验证输出。
- **探针自己踩的两个坑（顺手记下）**：① 第一版修改任务拿「把 `dist` 加进跳过名单」当目标，跑完才发现 `dist` 本来就在 `IGNORE_DIRS` 里——任务是空转，模型两次编辑互相抵消；换成一个真没有的目录（`htmlcov`）才测出东西。② 项目副本的临时目录名叫 `rag_probe_copy_*` 时，`tests/test_prompt.py` 那条「提示词里的 snake_case 词必须是工具名」的自检会把它误报成不存在的工具（副本根目录会写进提示词，带下划线的目录名撞上了正则）——不是项目缺陷，正常目录名不会踩到，但拿副本当靶子时目录名要避开 snake_case。
- **新增 4 条离线测试（`tests/test_rag_flow.py`）**：3 条钉提示词里 RAG 的位置——提到 `search_code_chunks` 的那一行说的正是「先缩范围、再精读」，description 里有「不返回代码正文」和与 `search_code` 的分工；1 条用脚本化的假模型把完整链走一遍——`search_code_chunks`（只回位置，`price * discount` 这行正文不许出现）→ `read_file`（第 4 行就是 RAG 指的那行）→ `edit_file`（成功，验证结果接在后面）→ 自动 `run_tests`（通过），trace 四步一条不少，最后文件真的改了、测试真的绿。全离线，0.2 s 跑完。

**接入 Agent：`search_code_chunks`（8.8 阶段）**

- **这一阶段只做一件事：把检索这条线接进 Agent。** 索引、切块、排序、评估从一开始就说「不是工具、不进 Agent」——攒到 8.8，检索质量有了（Hit@1 6/7）、扩展口留好了（scorer 列表），是时候让 Agent 用上它了。接法刻意普通：加一个 `SearchChunksTool`（`tools/search_chunks.py`），注册进 `ToolRegistry`，剩下的全是既有机制——schema 自动发给模型、调用走 `Agent → ToolExecutor → ToolRegistry → Tool`、结果自动回灌、trace 自动记录。**没有为它改 Agent 的一行代码，也没加任何新的调用路径。**
- **只给位置，不给正文**：每条结果是「`相对路径:起止行号` 符号 [类型] 分数 命中原因」。正文在 chunk 里明明就有（切块那一步就是为它切的），这里刻意不返回，两个原因：一是**省上下文**——一个类块几百行，十条结果就是几千行，而模型多半只看其中一条；二是**读到的永远是磁盘上当前的代码**——索引是快照，文件一改对应 chunk 就作废，返回位置让 `read_file` 现读，绕开了「缓存副本过期」这件事。行号格式和 `read_file` 是同一套（1 起、闭区间），拿到直接就能用。
- **命中原因留着**：分数拆开写（「限定名 Agent.run（+100）；路径里的 agent（+12）；更具体的 method（+10）」）。同样是 40 分，靠名字命中和靠正文命中含义完全不同——模型据此判断这条值不值得去看。原因里只会出现查询里的词、路径和符号名（这些模型自己都知道），不会把代码漏出来；有测试在真项目上拿「正文里才有的行」钉着这条。
- **参数两个**：`query` 必填（符号名 / 文件名 / 关键词都行），`top_k` 可选——默认 10，上限 50，要得比上限多就按上限给并在末尾说明（截断了不说的话，模型分不清「就这么多」和「只给了前几条」）。查不到返回「（没有找到…）」而不是报错——「没有」是有用的信息，报错会让模型以为是自己调用错了。
- **一个循环 import，用延迟导入绕开**：`tools/__init__.py` 会把所有工具模块 import 一遍，而 `index` 自己也 import `tools.base`——`search_chunks.py` 若在模块顶层 `from index import Retriever`，「先 import index」的那条路（比如 `python -m index`，本项目自带的命令）就会撞上只加载了一半的 index。所以真正 import 放在 `__init__` 里（`TYPE_CHECKING` 下的类型注解不算运行时 import）。两条 import 顺序都真的跑过，`python -m index` 照常，baseline 数字没变。
- **提示词跟着动了**：`tests/test_prompt.py` 有一条「注册表里的工具，提示词里必须点得到名」——新增工具时它会把提示词一起拉进来改，这次就是在「先用 list_files / search_code / search_code_chunks / code_summary 缩小范围」里加了名字。「提示词不重复工具的参数说明」这条规矩没破：什么时候用它、和 `search_code` 怎么分工，都写在工具自己的 `description` 里。
- **没动的**：`index/` 目录一个字节没改（Retriever、评分、切块、embedding、评估全原样），已有工具的实现代码一行没改，Agent / RepairLoop / Verifier / trace 的逻辑没碰。动过的只有装配处：`tools/search_chunks.py`（新）、`tools/__init__.py`（导出）、`main.py`（注册）、`agent/prompt.py`（那一句工具名）和 README。
- **怎么用**：`python main.py` 里问「Agent 的 tool-calling 循环在哪儿实现的」，模型会调 `search_code_chunks`，拿到位置后自己 `read_file` 去读那段；问「`Agent.run` 在哪儿」这种叫得出名字的，它直接排第 1。
- 测试（`tests/test_search_chunks.py`，25 条）：**结果转换**（类 / 方法各自的行范围是真实的、正文不在输出里、理由里看得到「限定名」、顺序就是 Retriever 给的顺序）；查不到不抛异常；**top_k**（限量、0 拒绝、超上限截断并说明、没截断就不说明）；**工具协议**（名字 / schema / query 必填 / 类型错 / 未知参数 / 空白查询都报 `ToolError`，默认 root = 项目根）；**走 ToolExecutor**（能跑、参数错变成失败结果而不是异常）；**Agent 侧**（schema 发给了模型、结果回灌到 tool 消息、回灌的是位置不是正文）；**真项目**（`Agent.run` 第 1 名落在 `agent/agent.py`、输出里没有任何代码行、现拼一个带时间戳的不存在查询确实为空——写死的词会命中这个测试文件自己，8.4 起就有这条规矩）。全部离线。

- ⚠️ 这台开发机上 `cmake` / `make` 都没装；`g++` 有，但装在一个 Qt 自带的 MinGW 里（`D:\qt\Tools\mingw730_64\bin\g++.exe`，GCC 7.3.0），不在 PATH 上，等于找不到。所以 `compile` / `build` 的日常路径仍然靠假编译器、假 `cmake`/`make`（丢一个 `.bat` 到 PATH 最前面）来测，验的是「命令拼得对不对、多步怎么串、结果怎么处理」。
- 但「真的能不能编」不能只靠假货证明，所以另外有两类**真跑**的测试：`CompileToolRealTest` 真的调一次 `cl.exe`（编带中文的源码 → 运行产物 → 比对输出；再故意编一个错的 → 确认错误原文回来了），`BuildToolRealTest` 真的调一次 `msbuild`（跑完确认 `.exe` 真的躺在 `out/` 里）。机器上没有 VS 时这两类整体跳过，不会在别的机器上变成假红。
- 真跑的那几条断言的是**产物真的存在**，不是只看退出码 0——「什么都没做就成功退出」的退出码也是 0。同理，`test_nothing_runs_when_a_project_name_is_refused` 这类验的是「拒绝了就一步都别跑」。
- `run_command`、`compile`、`build`、`edit_file` 是四个**能改系统状态**的工具（前五个只读）。`run_command` 的命令字符串由模型生成，等于让模型在你的机器上以你的权限执行任意命令；当前阶段刻意不做任何限制，这是有意为之的第一步，「命令能不能跑、跑在哪、跑多久」是后面阶段要单独设计的事。`compile` 和 `build` 能影响的只有「编哪个文件、用哪个工具、产物放哪儿」，所以反而比 `run_command` 更受约束。`edit_file` 是唯一会**改源码**的那个：它只能改 root 里已经存在的文件、只能改自己算得出来的一处，而且写坏了也不会留下半个文件——但「改得对不对」它管不了，那是模型的事。
- 系统提示词单独放在 `agent/prompt.py`，不写在 `agent/agent.py` 里：它是「怎么干活」的策略，改它不该碰到推理循环的代码；而且它是一段纯文本，可以单独测。
- 提示词里**不重复**工具的参数说明。那些在工具的 `description` 里，模型本来就收得到；抄一遍只是多出一处要跟着改的地方，改工具时漏掉就变成在说假话。有测试钉着这条（`timeout`、`source_root`、`build_dir`、`case_sensitive` 这些参数名不许出现在提示词里）。
- 提示词是 `build_system_prompt()` 拼出来的，不是一段写死的常量：里面要填运行时才知道的真值——项目根目录、操作系统、`run_command` 用的是哪个 shell（Windows 上是 `cmd.exe`，别处是 `/bin/sh`，这条不说模型会拿 `ls`、`;` 去试）。
- 有两条测试把提示词和工具注册表**对起来看**：注册表里的工具，提示词里必须点得到名（`calculator` 除外，它是演示用的例子，不参与代码分析）；提示词里冒出的、看着像工具名（snake_case）的词，注册表里必须真有。工具改名或新增时，这两条会把提示词一起拉进来改，不会留下一份在说废话的提示词。
- 两处豁免名单（`calculator`、举例用的函数名）也有测试盯着「名单里的词必须还在提示词/注册表里」，免得哪天例子删了、豁免却留着，把以后真叫这个名字的工具无声放过。
- 提示词里那条「行号以 `read_file` 返回的为准」换过三版，每一版都是被实测逼出来的：第一版只写「行号要准」，模型就给出一堆错行号（`read_file` 那时返回的是不带行号的原文，它只能自己数，而它数不准——抽查同一份回答：`search_code` 给过行号的地方全对，自己估的全错，比如把 `_render` 的定义行说成超时分支）；第二版改成「行号只能从 `search_code` 拿」，准了但引用变少，因为 `search_code` 只能给出含关键词的那几行；第三版给 `read_file` 加上行号，才改成以它为准。提示词里要求的事，工具得先做得到——做不到，模型只会给你编一个。
- 改之前先跑同样两个问题做了基线：回答能用，但引用是「大概第 105–160 行左右」这种，大部分结论干脆没行号。改完之后同样的两个问题，回答里出现的 10 处引用逐条回查**全部命中**；代价是第一个问题从 3 轮工具调用涨到 4 轮——想要准就得回去核。
